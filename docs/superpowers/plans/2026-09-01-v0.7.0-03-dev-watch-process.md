# MADS v0.7.0 Dev Watch and Process Supervision Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver a self-contained, cross-platform `mads dev` loop that watches relevant project files, uses Cargo incremental builds only when required, restarts for configuration-only changes, preserves the last successful app through compilation failures, and cleans up children.

**Architecture:** A pure state machine merges debounced file impacts and decides build/restart/process actions. A `notify` adapter supplies normalized events, Plan 1's Cargo builder performs incremental builds, and a Tokio supervisor owns the selected application process. Standard MADS applications receive a private file-based graceful-shutdown signal so replacement and Ctrl-C cleanup work without unsafe platform-specific signal APIs.

**Tech Stack:** Rust 2024, Rust 1.85 MSRV, Tokio processes/channels/time/filesystem, pinned `notify` 8.2.0, Cargo metadata, temporary directories, Axum graceful shutdown, and process-level fixture tests.

**Spec:** `docs/superpowers/specs/2026-09-01-v0.7.0-cli-dev-loop-diagnostics-design.md`

## Global Constraints

- Plans 1 and 2 must be complete.
- `mads dev` accepts the same `--package`/`-p`, `--bin`, and post-`--` application arguments as `mads run`.
- Rust, Cargo, schema, and migration changes trigger Cargo incremental build; `.env`/`mads.toml` alone restart without build.
- A mixed debounced batch triggers exactly one build; build impact dominates restart impact.
- Keep the last successful application running while a replacement builds.
- Failed replacement builds do not stop the last successful application and do not exit dev mode.
- If the initial build fails, keep watching with no application and retry only after a build-relevant change.
- Repeated events during a build collapse into at most one follow-up build using the newest state.
- There is no HMR, dynamic library reload, source patching, or external `cargo-watch` executable.
- Watch selected local packages/path dependencies and relevant workspace files; exclude `target`, `.git`, and editor/temp artifacts.
- Support Linux, macOS, and Windows without unsafe code.
- Keep diagnostic/error output secret-safe and stream Cargo/rustc messages unchanged.
- Keep Rust 1.85 and line coverage at least 85%.

Add `notify.workspace = true` to `mads-cli`. Define:

```rust
pub(crate) const MADS220: &str = "MADS220";

#[derive(Clone, Copy, Debug, Eq, Ord, PartialEq, PartialOrd)]
pub(crate) enum ChangeImpact { None, Restart, Rebuild }

pub(crate) struct WatchRoot {
    path: PathBuf,
    recursive: bool,
}

pub(crate) struct WatchSet {
    workspace_root: PathBuf,
    package_root: PathBuf,
    local_roots: Vec<PathBuf>,
    excluded_package_roots: Vec<PathBuf>,
    notify_roots: Vec<WatchRoot>,
}

impl WatchSet {
    pub(crate) fn for_application(
        project: &CargoProject,
        application: &ResolvedApplication,
    ) -> Self;
    pub(crate) fn roots(&self) -> &[WatchRoot];
    pub(crate) fn classify(&self, path: impl AsRef<Path>) -> ChangeImpact;
}

impl WatchRoot {
    pub(crate) fn path(&self) -> &Path;
    pub(crate) const fn recursive(&self) -> bool;
}
```

Build `excluded_package_roots` from local Cargo metadata packages that are not
reachable from the selected package. For a path below nested package roots,
the longest matching package root owns it; source changes rebuild only when
that owner is reachable. Build `notify_roots` from recursive reachable package
roots plus a non-recursive workspace root entry for workspace `Cargo.toml` and
`Cargo.lock` when those files are not already covered.

Classification order is:

1. reject paths under any `target` or `.git` component and filenames ending in
   `~`, `.swp`, `.swx`, `.tmp`, or `.DS_Store`; reject paths owned by an
   excluded package root;
2. selected package `.env`/`mads.toml` -> `Restart`;
3. `.rs` below a reachable package root, a reachable package `Cargo.toml`, the
   workspace `Cargo.toml`/`Cargo.lock`, anything below selected-package
   `migrations/`, and schema paths -> `Rebuild`;
4. all other paths -> `None`.

Rename events classify both old and new paths. Remove/create/modify events are
accepted; access-only events are ignored.

Cover these sequences explicitly:

- initial build failure -> no app, remain watching;
- config-only event with no successful binary -> no action;
- rebuild starts while v1 remains active;
- build failure -> v1 remains active;
- successful v2 build -> stop v1 then start v2;
- restart event during build -> successful replacement starts once with current
  config and no second restart;
- rebuild events during build -> one queued follow-up build;
- multiple restart events -> one restart;
- app exits unexpectedly -> retain last binary, wait for the next relevant
  change rather than entering a crash loop;
- shutdown -> stop active app, cancel/kill active build, exit.

- [ ] **Step 3: Define events, phases, and actions exactly**

Create:

```rust
#[derive(Clone, Debug)]
pub(crate) enum DevEvent {
    Start,
    Changed(ChangeImpact),
    BuildSucceeded(BuiltApplication),
    BuildFailed,
    ApplicationExited,
    Shutdown,
}

#[derive(Clone, Debug, Eq, PartialEq)]
pub(crate) enum DevAction {
    Build,
    Start(BuiltApplication),
    Stop,
    Restart(BuiltApplication),
    Exit,
}

pub(crate) struct DevState {
    last_successful: Option<BuiltApplication>,
    application_running: bool,
    build_running: bool,
    pending: ChangeImpact,
    shutting_down: bool,
}
```

`ChangeImpact::None` yields no action. While building, merge changes into
`pending`. On success, replace `last_successful`; if an app runs emit
`Stop, Start(new)`, otherwise `Start(new)`. If pending is `Rebuild`, schedule
one subsequent `Build`; pending `Restart` is consumed by starting the newly
built binary. A config-only event while an app runs emits
`Restart(last_successful.clone())`, making the artifact to restart explicit.
On build failure, keep active state and schedule a follow-up only for pending
`Rebuild`.

On unexpected app exit, set `application_running = false` and retain
`last_successful`. A later config-only event emits `Start(last_successful)`;
a rebuild event builds first.

- [ ] **Step 4: Implement the concrete event loop**

Define the exact driver boundary used by scripted tests and by the production
Cargo/process adapter:

```rust
use std::{future::Future, pin::Pin};

type DriverFuture<'a, T> =
    Pin<Box<dyn Future<Output = Result<T, CliError>> + Send + 'a>>;

trait DevDriver {
    fn build(
        &mut self,
        target: ResolvedApplication,
    ) -> DriverFuture<'static, BuiltApplication>;
    fn start(
        &mut self,
        built: BuiltApplication,
        arguments: Vec<OsString>,
    ) -> DriverFuture<'_, ()>;
    fn stop(&mut self) -> DriverFuture<'_, StopOutcome>;
    fn application_exited(&mut self) -> Result<bool, CliError>;
}

async fn run_dev_with<D: DevDriver>(
    command: ApplicationCommand,
    driver: &mut D,
    watch_set: WatchSet,
    events: WatchEvents,
) -> Result<(), CliError>;
```

`ScriptedDevDriver` records calls and returns queued results without starting
processes. `ProductionDevDriver` owns at most one `ApplicationProcess`; its
methods delegate to `build_application`, `spawn_dev_application`, `stop`, and
`try_wait`. `run_dev_with` owns the state and uses
`tokio::select!` over:

- Ctrl-C;
- next debounced change;
- an active build future;
- periodic `ApplicationProcess::try_wait` checks.

Production sequence:

1. resolve target and create `WatchSet`/`WatchEvents` before initial build;
2. print `mads dev: watching <package>/<binary>`;
3. perform initial Cargo incremental build;
4. execute `DevAction`s in order;
5. print rebuild/restart/build-failed/exit notices;
6. on Ctrl-C stop the app gracefully, cancel/drop the active Cargo child with
   `kill_on_drop`, await cleanup, and return success;
7. return exit 1 only when metadata, watcher, or supervisor infrastructure can
   no longer continue.

Refactor `build_application` so cancellation always owns and drops a Tokio
Cargo child configured with `kill_on_drop(true)`. Do not buffer compiler output.
