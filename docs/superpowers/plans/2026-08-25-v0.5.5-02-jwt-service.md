# MADS.rs v0.5.5 JWT Service Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver an application-scoped, auto-configured `JwtService` with strict access/refresh profiles, eight pinned algorithms, named-key rotation, typed claims, and redacted failures.

**Architecture:** `mads-common::jwt` parses Passport configuration into an immutable validation policy and key-ring description, validates configuration during side-effect-free analysis, then constructs and caches `jsonwebtoken` encoding/decoding keys after graph validation. `JwtService` owns cryptography and registered claims; application custom claims remain typed JSON objects. The existing conditional-default engine activates the service only for a direct provider dependency in this plan; guard activation is added by Plan 4.

**Tech Stack:** Rust 2024, Rust 1.85.0, `jsonwebtoken` =10.3.0 with `rust_crypto` and `use_pem`, Serde, `serde_json`, `inventory`, TOML configuration from Plan 1.

**Spec:** `docs/superpowers/specs/2026-08-25-v0.5.5-passport-jwt-and-cookies-design.md`

## Global Constraints

- Complete Plan 1 first; consume its `ConfigDocument`, string-array, source attribution, and `Config::resolve_path` contracts unchanged.
- Keep `mads-core` free of JWT and cryptography dependencies; JWT implementation stays under the `mads-common` `jwt` feature.
- Pin `jsonwebtoken` exactly to `=10.3.0`; do not accept a newer MSRV-incompatible release.
- Support only HS256, HS384, HS512, RS256, RS384, RS512, ES256, and ES384; never infer or widen algorithms from token headers.
- Simple `passport.secret` mode supports exactly one HMAC algorithm and defaults to HS256.
- Enforce HMAC minimum secret lengths of 32, 48, and 64 bytes for HS256, HS384, and HS512 respectively.
- Named key-ring mode requires a non-empty root algorithm allowlist, one algorithm per key, one active signing key, and `kid` on every token.
- The active key signs and verifies; previous keys verify only.
- Support inline and file-backed RSA/EC PEM; reject both forms together and resolve files through Plan 1 provenance.
- Require `exp`, `iat`, `typ`, and `token_use`; validate optional `nbf`; enforce configured issuer/audience; default skew 0 and maximum token bytes 8192.
- MADS-issued token kinds are exactly `mads-access+jwt`/`access` and `mads-refresh+jwt`/`refresh`.
- Signing requires a positive lifetime and explicit token kind; verification requires an explicit expected kind.
- Custom claims must serialize as an object and may not collide with MADS-owned names.
- Expose only explicit `decode_header` and `decode_unverified`; do not add a plain `decode` API.
- Never expose secrets, PEM bytes, tokens, claims, or resolved configuration values through diagnostics, errors, reports, `Display`, or `Debug`.
- Refresh persistence, rotation, revocation, reuse detection, and endpoints remain application responsibilities.
- Keep auto-configuration identifier `mads.common.passport.jwt`; use `MADS120` for JWT operations and `MADS121` for auto-configuration.
