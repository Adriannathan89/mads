# MADS v0.7.0 Application Inspection Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implement the private child-application inspection protocol and deliver deterministic `mads routes`, `mads graph`, and `mads doctor` without constructing providers or starting runtime infrastructure.

**Architecture:** Core converts live graph analysis into owned framework-neutral snapshots. Common intercepts a complete private request inside `Mads::run::<AppModule>()`, loads read-only configuration, analyzes the rooted application, adds scoped HTTP metadata, writes a versioned report, and returns before build/lifecycle/bind. The CLI builds the selected binary, supervises handshake/report files, validates the envelope, and renders command-specific human output.

**Tech Stack:** Rust 2024, Rust 1.85 MSRV, existing inventory/module/route/Passport metadata, Serde JSON for private transport, Tokio child supervision, `tempfile`, Cargo fixtures, and the existing MADS diagnostic model.

**Spec:** `docs/superpowers/specs/2026-09-01-v0.7.0-cli-dev-loop-diagnostics-design.md`

## Global Constraints

- Plan 1 must be complete; consume its `TargetSelection`, `CargoProject`, `ResolvedApplication`, `build_application`, `BuiltApplication`, and `CliError` interfaces.
- Support only binaries that reach `Mads::run::<AppModule>()` during inspection.
- Check the selected application's MADS version before launch, then validate protocol version and request token at runtime.
- Inspection must not call `MadsBuilder::build`, provider constructors, auto-configuration appliers, lifecycle hooks, database pool creation, migrations, listener binding, router registrars, or request handlers.
- Configuration loading is read-only and follows standard run: optional `.env`, optional `mads.toml`, then `MADS_*` overrides.
- Doctor never connects to PostgreSQL; database status is metadata/configuration evidence only.
- Keep protocol items `#[doc(hidden)]`; the wire format is not a stable public API or JSON CLI feature.
- Keep output deterministic and useful on invalid graphs/routes; return exit 1 when the selected report contains a required failure.
- Generic configuration output contains keys/sources/status only, never raw values.
- Preserve normal `Mads::run` behavior when no complete inspection request is present.
- Keep public APIs documented, unsafe code forbidden, Rust 1.85, and coverage at least 85%.

- [ ] **Step 4: Expose selected route records without constructing controllers**

Add this crate-private iterator to `HttpApplicationScope`:

```rust
pub(crate) fn route_records(
    &self,
) -> impl Iterator<Item = (&ControllerRouteDescriptor, &RouteContractDescriptor, &RouteDescriptor)> {
    self.controllers.iter().flat_map(|controller| {
        controller.descriptor().contracts().iter().flat_map(move |contract| {
            contract.routes().iter()
                .filter(move |route| controller.selects(route))
                .map(move |route| (controller.descriptor(), contract, route))
        })
    })
}

pub(crate) fn for_rooted_inspection(
    module_graph: Option<&ModuleGraph>,
) -> Result<Self> {
    let controllers = module_graph
        .map(Self::rooted_controllers)
        .unwrap_or_default();
    #[cfg(feature = "jwt")]
    let guards = match module_graph {
        Some(graph) => Self::selected_guards(Some(graph), &controllers),
        None => Vec::new(),
    };
    Ok(Self {
        controllers,
        #[cfg(feature = "jwt")]
        guards,
    })
}
```

This iterator reads descriptors only. It must not call registrar accessors or
resolve a controller. Unlike the existing complete-catalog meaning of
`for_module_graph(None)`, a failed rooted analysis exposes no unrelated
inventory routes.

- [ ] **Step 5: Assemble one report from read-only analysis**

Implement:

```rust
pub(crate) fn inspect_standard_application<M: Module>(
    root: &Path,
    kind: InspectionKind,
) -> InspectionReport;
```

The function must:

1. load conventional configuration; on failure copy diagnostics and continue
   analysis with `Config::empty()` so graph/routes remain useful;
2. root `Mads::builder_with_config(config)` at `M`;
3. register `HttpRuntimeMode::Automatic` inputs for server and CORS;
4. call `builder.analyze()` exactly once and convert it to
   `GraphInspectionSnapshot`;
5. derive `HttpApplicationScope` with
   `for_rooted_inspection(analysis.module_graph())`;
6. collect all selected route records, sorted by method/path/controller/trait;
7. call scoped descriptor validation and append any route diagnostics;
8. under `jwt`, run scoped strategy preflight and append its diagnostics;
9. build doctor checks in fixed group order:
   `configuration`, `module graph`, `providers`, `routes`,
   `guards/strategies`, `server/CORS`, `auto-configuration`;
10. mark `failed` when any required check or diagnostic fails.

Map active auto-configurations to `PASS`, skipped to `SKIPPED`, overridden to
`OVERRIDDEN`, and failed to `FAILED`. Database reports may inspect only their
existing redacted evidence; do not call `Database::from_config` or an applier.

pub(crate) fn try_run_inspection<M: Module>(
