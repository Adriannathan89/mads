# MADS v0.7.0 Database Schema-Diff Generation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implement the single no-name `mads db generate` command that recursively loads split Diesel schema files, compares their supported table shape with live PostgreSQL, and atomically writes review-required reversible `up.sql`/`down.sql` without invoking an external Diesel CLI.

**Architecture:** Reuse Diesel 2.2's table-macro syntax parser to turn source files into an owned normalized schema model. Read a matching PostgreSQL catalog snapshot through the existing managed database boundary, compute typed reversible operations, render only validated/quoted SQL, and publish a timestamped directory after the complete plan succeeds. Unsupported database objects are retained as warnings or hard safety failures; they are never guessed.

**Tech Stack:** Rust 2024, Rust 1.85 MSRV, Diesel/PostgreSQL 2.2.12, `diesel_table_macro_syntax` 0.2.0, `syn` 2, `BTreeMap`, PostgreSQL `pg_catalog`, `tempfile`, and real PostgreSQL 16 integration tests.

**Spec:** `docs/superpowers/specs/2026-09-01-v0.7.0-cli-dev-loop-diagnostics-design.md`

## Global Constraints

- Plan 1 must be complete; Plans 2 and 3 are independent of this plan.
- The only generation grammar is `mads db generate [--package <package>]`.
- Reject a positional name, `--diff-schema`, `--bin`, application arguments, and duplicate package selectors with exit 2.
- Discover `src/schema.rs` plus recursive `src/schema/**/*.rs`; support both in one project and merge deterministically.
- Invoke no `diesel`, `diesel-cli`, shell, or other external generator executable.
- Use the existing selected-package configuration chain exactly: optional `.env`, required `mads.toml`, `MADS_*`, then `database.url`.
- PostgreSQL is the only backend.
- Support create/drop table, add/drop column, type/nullability changes, and primary keys on created/recreated tables.
- `down.sql` reverses the supported shape toward the captured live state; data restoration is not promised and destructive operations are warned.
- Defaults, non-primary indexes, checks, triggers, exact FK actions, risky casts, and required columns on populated tables are not silently synthesized.
- Quote every schema/table/column identifier; never interpolate a database-provided identifier unquoted.
- Never print credentials or raw database URLs.
- Generate no files on no-diff or failure; never overwrite; publish the final directory atomically.
- Never apply generated SQL automatically.
- Keep public APIs documented, unsafe code forbidden, Rust 1.85, and coverage at least 85%.

```rust
pub(crate) enum PgType {
    Bool, SmallInt, Integer, BigInt, Real, DoublePrecision, Numeric,
```

- [ ] **Step 5: Implement deterministic discovery and Diesel parser reuse**

`DesiredSchema::load`:

1. includes `src/schema.rs` if it is a regular file;
2. recursively walks `src/schema/` with `read_dir`, never follows directory
   symlinks, and includes `.rs` regular files;
3. canonicalizes containment under the package root;
4. sorts normalized relative paths;
5. parses each with `syn::parse_file`;
6. recursively visits file/inline-module `Item::Macro` values whose path ends
   in `table`;
7. parses macro tokens with `syn::parse2::<diesel_table_macro_syntax::TableDecl>`;
8. converts `schema`, `sql_name`, primary keys, columns, `sql_name`, and
   `max_length` into the owned model;
9. defaults schema to `public` and primary key to `id`;
10. rejects duplicate qualified table identities with both relative file names.

Accept inert documentation/lint attributes left by the Diesel parser. Reject
`cfg`/`cfg_attr` because a source-only CLI cannot reliably evaluate the
selected binary's feature set.

- [ ] **Step 3: Define typed operations and inverse construction**

Create:

```rust
#[derive(Clone, Debug, Eq, PartialEq)]
pub(crate) enum Operation {
    CreateTable(TableSchema),
    DropTable(TableSchema),
    AddColumn { table: QualifiedTableName, column: ColumnSchema },
    DropColumn { table: QualifiedTableName, column: ColumnSchema },
    AlterType {
        table: QualifiedTableName,
        column: String,
        from: PgType,
        to: PgType,
    },
    SetNotNull { table: QualifiedTableName, column: String },
    DropNotNull { table: QualifiedTableName, column: String },
}

pub(crate) struct MigrationWarning {
    pub(crate) subject: String,
    pub(crate) message: String,
}

pub(crate) struct MigrationPlan {
    up: Vec<Operation>,
    down: Vec<Operation>,
    warnings: Vec<MigrationWarning>,
}

pub(crate) fn plan_diff(
    desired: &DesiredSchema,
    live: &LiveSchema,
) -> Result<MigrationPlan, CliError>;
```

Every operation owns enough state for `inverse()`. Construct `down` by
reversing `up` and mapping each operation to its exact inverse; never recompute
down from a mutated intermediate schema.

- [ ] **Step 4: Apply deterministic/safe ordering**

Use this up order:

1. create missing tables by qualified name;
2. add columns by table/desired ordinal;
3. alter types by table/live ordinal;
4. change nullability by table/live ordinal;
5. drop columns by table/reverse live ordinal;
6. drop tables in reverse FK dependency order, then qualified name.

Reject FK cycles among dropped tables because exact FK removal/recreation is
outside scope. Reject dropping a table referenced by a retained table. Order
dropped tables child-before-referenced-parent, so reversed down operations
recreate parent-before-child. Created tables have no synthesized FKs. `down`
is exact reverse operation order.

Existing-table PK changes are unsupported hard failures. Create/recreate table
operations include the captured/declaration PK. A dropped PK column on a
retained table is a hard failure rather than silently changing the key.

Unsupported defaults/indexes/checks/triggers/FKs do not create operations.
Attach warnings when an operation touches their table/columns; unaffected
unsupported objects remain untouched and need no warning.

- [ ] **Step 3: Implement identifier and type rendering**

`quote_identifier` always surrounds with `"` and doubles internal `"`.
Only `PgType::to_sql` may render type text; it returns static/canonical fragments
plus validated numeric lengths and recursive array suffixes. Never accept a raw
type string in `Operation` or SQL APIs.

Render statements:

```text
CREATE TABLE ... (columns..., PRIMARY KEY (...));
DROP TABLE ...;
ALTER TABLE ... ADD COLUMN ...;
ALTER TABLE ... DROP COLUMN ...;
ALTER TABLE ... ALTER COLUMN ... TYPE ... USING "column"::type;
ALTER TABLE ... ALTER COLUMN ... SET NOT NULL;
ALTER TABLE ... ALTER COLUMN ... DROP NOT NULL;
```

Do not emit `CASCADE`, `IF EXISTS`, `IF NOT EXISTS`, `BEGIN`, `COMMIT`, defaults,
or synthetic SQL that changes semantics.

```rust
pub(crate) async fn generate(root: &Path) -> Result<Vec<String>, CliError> {
    let desired = DesiredSchema::load(root)?;
    let project = load_project(root)?;
    let database = project.connect()?;
    let namespaces = desired.namespaces();
    let live_result = LiveSchema::load(&database, &namespaces).await;
    database.close();
    let live = live_result?;
    let plan = plan_diff(&desired, &live)?;
    if plan.is_empty() {
        return Ok(vec!["schema is up to date".into()]);
    }
    let rendered = render_migration(&plan);
    let path = publish_migration(root, &rendered, &SystemMigrationClock)?;
    let mut lines = rendered
        .warnings
        .iter()
        .map(|warning| format!("warning: {warning}"))
        .collect::<Vec<_>>();
    lines.push(format!("generated {}", path.display()));
    lines.push("review up.sql and down.sql before applying".into());
    Ok(lines)
}
```
