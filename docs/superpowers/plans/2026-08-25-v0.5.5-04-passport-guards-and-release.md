# MADS.rs v0.5.5 Passport Guards and Release Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add managed Passport strategies, typed principals, inheritable route/method `#[guard]` policies, Bearer/cookie authentication, native Axum guards, and finish the v0.5.5 release.

**Architecture:** Route macros emit complete effective guard metadata and typed predicate adapters; strategy macros emit type-erased adapters for concrete managed `PassportStrategy` implementations. Startup validates the complete v0.5.5 guard/strategy catalog before provider construction and extends JWT auto-configuration requirements with guarded routes. At request time one shared guard runtime extracts exactly one token, invokes framework JWT verification before strategy validation, enforces principal policy, installs typed request extensions, and maps failures to stable HTTP responses.

**Tech Stack:** Rust 2024, Rust 1.85.0, Axum 0.8.9, Tower 0.5, `inventory`, Syn 2, Quote 1, `trybuild`, Plans 1-3 configuration/JWT/cookie contracts.

**Spec:** `docs/superpowers/specs/2026-08-25-v0.5.5-passport-jwt-and-cookies-design.md`

## Global Constraints

- Complete Plans 1-3 before this plan; Plans 2 and 3 may execute independently
  after Plan 1.
- Compile Passport only under `all(feature = "http", feature = "jwt")`; cookie token sources additionally require `cookies`.
- Keep `JwtService` as the stable cryptographic utility; application polymorphism belongs to `PassportStrategy`.
- A strategy is eligible in v0.5.5 only when it implements `PassportStrategy`, has `#[passport_strategy]` metadata, and its concrete type is a managed provider.
- One custom strategy with a built-in name overrides the built-in; duplicate custom names are ambiguous; different names coexist.
- `jwt` is the only built-in strategy and uses access tokens. `jwt-refresh` is application-defined and uses refresh tokens.
- Framework JWT signature, registered-claim, and token-kind verification always occurs before application strategy validation.
- A strategy receives verified typed claims plus read-only request context and returns a typed principal analogous to NestJS `request.user`.
- `#[guard]` is legal only directly beneath a MADS `#[routes]` trait or route verb method; it is not a controller/free-function/native-handler attribute.
- Route-level policy is inherited; method policy replaces only supplied fields; `#[guard(skip)]` is the sole inherited-policy opt-out.
- Bearer is the default and one guard uses one source only; no source fallback.
- Roles, permissions, and predicates are separate AND clauses; `any`/`all` semantics are explicit; multiple predicates are ANDed.
- Predicates have compile-checked `fn(&Principal) -> bool` signatures and are synchronous principal-only checks.
- Authentication/strategy rejection maps to generic 401 plus `WWW-Authenticate: Bearer`; authorization maps to 403; operational failure maps to 500.
- Cookie target missing/malformed/duplicated maps to generic 401; ordinary cookie extraction stays 400.
- Never expose tokens, claim values, principal values, cookie names/values, keys, secrets, or internal strategy errors in HTTP responses or framework diagnostics.
- Keep refresh storage/rotation/revocation entirely in application strategy/service code.
- Use `MADS130` for strategy registration/resolution/type failures and `MADS131` for guard metadata/runtime-policy failures.
- v0.6.0 module reachability/export scoping must be additive over the descriptors created here; do not implement module scoping now.
- v0.5.6 owns CORS and HTTP auto-binding; do not implement either in this release.

> **Roadmap supersession (v0.6.0):** The planned v0.5.6 CORS and HTTP
> auto-binding milestone was merged into v0.6.0 so it could share the root
> module scope with provider, route, guard, and strategy discovery.
