# MADS v0.6.0 Modules, CORS, and Automatic HTTP Runtime Design

**Status:** Approved design, pending implementation planning
**Target:** MADS v0.6.0
**Date:** 2026-08-27

## Context

MADS v0.5.5 has a deterministic concrete-type provider graph, official
auto-configuration, generated Axum routing, Passport guards and strategies,
explicit configuration sources, and explicit HTTP serving. The current public
startup path still requires users to construct configuration, build an
application, and call `serve` themselves. Static `#[module]` declarations are
metadata-only and do not select or bound an application.

The old roadmap split the next work between v0.5.6 (CORS and HTTP
auto-binding) and v0.6.0 (modules and visibility). Those capabilities depend
on the same question: which application is being started? They therefore ship
as one v0.6.0 release built around a root module and one scoped analysis
pipeline.

The desired standard application is:

```rust
// src/app.rs
use mads::prelude::*;

use crate::delivery::http::user::UserHttpModule;

#[module(imports = [UserHttpModule])]
pub struct AppModule;
```

```rust
// src/delivery/http/user/mod.rs
use mads::prelude::*;

mod controller;
mod input;
mod response;

pub use controller::*;
pub use input::*;
pub use response::*;

#[module]
pub struct UserHttpModule;
```

```rust
// src/main.rs
use mads::prelude::*;

mod app;
mod application;
mod delivery;
mod domain;
mod infrastructure;

use app::AppModule;

#[mads::main]
async fn main() -> Result<(), HttpRuntimeError> {
    Mads::run::<AppModule>().await
}
```

The module syntax is inspired by NestJS module definitions, but MADS keeps its
existing automatic provider and controller discovery. Rust namespaces define
ownership; users do not repeat declarations in `providers`, `controllers`, or
`exports` lists.

## Goals

- Make `Mads::run::<AppModule>().await` the standard build-and-run source.
- Turn `#[module(imports = [...])]` into an application boundary.
- Derive descriptor ownership from Rust namespaces.
- Enforce direct-import and plain-`pub` cross-module visibility.
- Scope provider, controller, route, guard, strategy, and official
  auto-configuration analysis to the selected application.
- Preserve automatic discovery and exactly-once construction.
- Automatically load conventional configuration and bind one HTTP listener.
- Add strict application-wide CORS configuration.
- Preserve the existing builder and native Axum APIs as low-level escape
  hatches.
- Merge the old v0.5.6 roadmap scope into v0.6.0.

## Non-goals

v0.6.0 does not add:

- trait or interface bindings;
- `Inject<dyn Trait>`;
- request-validation framework work;
- generic typed configuration derives or schemas;
- automatic migration discovery or execution;
- third-party auto-configuration registration;
- module-level HTTP paths or prefixes;
- TLS, Unix sockets, multiple listeners, socket tuning, or HTTP/2-specific
  configuration;
- proxy-trust configuration;
- regex, glob, or dynamic CORS origin predicates.

Concrete-type dependency injection remains the supported model. Route
contracts remain the exclusive owner of HTTP paths and prefixes.

## Chosen architecture

### Core owns generic application scope

`mads-core` owns all framework-independent module behavior:

- the marker contract emitted by `#[module]`;
- module descriptors and direct-import metadata;
- deterministic module graph construction;
- namespace ownership indexes;
- scoped provider dependency analysis;
- direct-import visibility enforcement;
- `MadsBuilder::root::<M>()`;
- retained read-only module graph inspection.

Core must not depend on Axum, HTTP routes, Passport, CORS, listener binding, or
common integration types.

### Common consumes core scope

`mads-common` filters its existing inventories through the core application
scope. It owns:

- reachable controller and route selection;
- scoped guard and Passport strategy selection;
- the standard automatic configuration loader;
- HTTP server and CORS auto-configuration;
- final router configuration;
- automatic TCP binding and shutdown coordination;
- `MadsRunExt`, `configure_router`, and `serve_router`.

Database and JWT remain official auto-configurations. They receive scoped
requirements through the same core pipeline rather than through a second HTTP
startup planner.

### Facade owns the standard experience

`mads::prelude::*` exports the application-facing module and run API, including
`Mads`, `MadsRunExt`, `HttpRuntimeError`, and the declaration macros.

`MadsBuilder` remains public through `mads::core`, but is removed from the
standard prelude. The inherent `Mads::builder()` and
`Mads::builder_with_config()` methods remain available for compatibility and
are documented as low-level entry points.

## Module declaration contract

### Supported syntax

The macro accepts only unit structs without generics:

```rust
#[module]
pub struct UserHttpModule;

#[module(imports = [UserHttpModule, InfrastructureModule])]
pub struct AppModule;
```

The only v0.6.0 argument is `imports = [...]`. Empty imports use the
argument-free form. The macro rejects unknown keys, repeated `imports` keys,
non-array imports, and unsupported struct forms with compile-time diagnostics.

Each import must resolve to a type produced by `#[module]`. The macro-generated
marker implementation gives graph construction stable type identity and a
descriptor reference without requiring the caller to register anything.

There are deliberately no `providers`, `controllers`, `exports`, or `path`
arguments.

### Descriptor metadata

A module descriptor contains:

- stable and runtime type identity;
- the enclosing Rust namespace from `module_path!()`;
- declaration location;
- direct imports in declaration order.

Provider, controller, route, guard, and strategy descriptors gain declaration
namespace metadata. MADS-owned macros always emit it. Compatibility
constructors for manually assembled/native descriptors remain usable; a
manual descriptor without namespace metadata is treated as unowned unless it
uses the additive namespace metadata API.

Descriptor constructors remain value-free and inventory-safe. Type IDs are
obtained through function pointers as in the existing descriptor model.

## Namespace ownership

A descriptor is owned by the annotated module whose namespace is its nearest
ancestor.

For example:

```text
crate::delivery::http::user                  UserHttpModule
crate::delivery::http::user::controller      UserController
crate::delivery::http::user::admin           AdminHttpModule
crate::delivery::http::user::admin::handler  AdminController
```

`UserController` belongs to `UserHttpModule`; `AdminController` belongs to
`AdminHttpModule`. Importing `UserHttpModule` does not implicitly import
`AdminHttpModule`.

Matching is performed on complete Rust path segments. A namespace such as
`crate::user_extra` is not a descendant of `crate::user`.

Two `#[module]` declarations in the same Rust namespace are invalid because
ownership would be ambiguous. Scoped builds report this only when that
namespace participates in the selected application; rootless builds validate
the complete catalog.

Descriptors outside every annotated namespace are unowned. Unowned providers
are not application roots; they enter a scoped application only through a
reachable dependency path or an explicit low-level builder operation.

## Module graph construction

`Mads::run::<AppModule>()` and `MadsBuilder::root::<AppModule>()` select one root
module. Graph construction:

1. resolves the root descriptor;
2. walks direct imports in declaration order;
3. records every direct edge, including both sides of a diamond;
4. deduplicates module activation by `TypeId`;
5. diagnoses repeated imports in one import list;
6. diagnoses self-imports and cycles with the import chain and source
   locations;
7. produces a deterministic reachable-module order.

Repeated paths through a diamond never register or construct a module or
provider twice. An import cycle is never broken implicitly.

A builder root can be selected at most once. Repeating root selection is an
error rather than last-write-wins behavior.

Rootless `MadsBuilder` preserves the v0.5.5 complete-catalog analysis and
construction behavior.

## Activation and provider resolution

Every provider, controller, route, guard, and strategy owned by a reachable
module is activated, even when no other provider currently depends on it.
This preserves MADS automatic discovery within explicit module boundaries.

The provider closure starts with:

- every provider owned by a reachable module;
- controller and guard provider requirements from reachable HTTP metadata;
- explicitly provided or preconstructed low-level values;
- framework-owned values such as `Config`.

Analysis then follows dependencies until it reaches a fixed point:

- an unowned provider is included when its concrete type is required;
- an owned provider is included only through valid module visibility;
- an applicable official auto-configuration may satisfy a missing
  infrastructure type;
- dependencies added by selected providers or auto-configurations are analyzed
  in the same deterministic pass.

Each selected provider is constructed exactly once by `TypeId`. Existing
duplicate and ambiguous concrete-provider diagnostics remain in force.
Explicitly provided or preconstructed low-level values retain their current
override behavior and are treated as deliberate application inputs rather
than namespace-owned declarations.

## Module visibility

Visibility is checked in a module context.

- A module can use all providers it owns, including private and restricted
  Rust declarations.
- A provider owned by another module is visible only if that module is a
  direct import and the provider uses unrestricted `pub` visibility.
- `pub(crate)`, `pub(super)`, `pub(in ...)`, and private declarations remain
  internal to their owning MADS module.
- Imports are not transitive exports. If A imports B and B imports C, A cannot
  consume C unless A also imports C.

When an owned provider depends on an unowned provider, resolution carries the
owned provider's module context through the unowned chain. An unowned use case
therefore cannot bypass a missing module import. Once resolution enters an
owned provider in another module, that provider's module becomes the context
for its own dependencies.

A boundary error distinguishes an absent import from a non-public provider and
includes the requesting context, target owner, dependency path, and available
source locations. It must not be downgraded to a generic missing-provider
error.

## Retained module inspection

Rooted `GraphAnalysis` and the built `Mads` application retain a read-only
module graph alongside the existing provider graph and construction plan. The
inspection model exposes:

- root module identity;
- reachable module identities and locations;
- deterministic traversal order;
- direct import edges;
- selected provider ownership, including explicit `None` for unowned
  providers.

Rootless applications expose no selected root while their existing global
catalog and provider graph APIs remain unchanged. Inspection returns borrowed,
immutable data and cannot mutate application scope.

## Scoped common catalogs

### Routes and controllers

`RouteCatalog` remains a global inventory API. Router construction for a rooted
application selects only controllers and routes whose owner is reachable.
Route validation, conflict detection, controller resolution, and registration
operate on that selected set.

All reachable routes share one Axum router. Conflicting method/path pairs are
therefore diagnosed globally across the complete reachable application, not
separately per module.

Rootless applications preserve complete-catalog routing behavior.

### Guards and Passport strategies

Only guards attached to selected routes participate in HTTP preflight. Guard
providers follow ordinary provider visibility.

Strategy lookup is evaluated for each guard's module visibility context:

- an owned guard uses its owning module;
- an unowned guard inherits the route/controller's current module context;
- a strategy in another module must be public and directly imported;
- imports do not make strategies transitively visible.

The built-in `jwt` strategy is a global fallback. Exactly one visible custom
strategy with the same name overrides that fallback in its context. Two or
more visible custom strategies with the same name are ambiguous. Same-named
strategies may coexist when no guard context can see both.

The global `GuardCatalog` and `PassportStrategyCatalog` remain available for
low-level tooling; scoped preflight uses filtered views.

## Scope-aware auto-configuration

The core auto-configuration context gains read-only access to the selected
application scope. Official integrations derive requirements only from that
scope:

- database configuration is required only by reachable dependencies;
- JWT configuration is required only by reachable authentication paths;
- automatic server binding is relevant only to a standard run with reachable
  managed routes;
- CORS is relevant to the selected HTTP application;
- unreachable module requirements are ignored.

Auto-configuration remains closed to third-party registration in v0.6.0.

Explicit providers continue to override official provider-producing
auto-configurations. Existing `Active`, `Skipped`, `Overridden`, and `Failed`
report semantics remain.

HTTP retains distinct decisions under these identifiers:

- `mads.common.http.server`
- `mads.common.http.cors`

For standard automatic execution, the server decision is `Active` when routes
exist, `Skipped` when no managed route exists, and `Failed` for invalid
configuration. Choosing the low-level builder means automatic listener
ownership is `Overridden`; explicit `serve` and `serve_router` own the address.

CORS is `Active` when configured for the applicable HTTP execution, `Skipped`
when absent or irrelevant, and `Failed` when invalid. A supplied native router
is an applicable low-level HTTP execution even if the managed route scope is
empty.

Reports retain identifiers, status, reason codes, requirement subjects,
configuration keys, and source labels. They never retain resolved hostnames,
ports, origins, methods, header values, secrets, or other loaded values.
Internal server and CORS plan values use redacted `Debug` implementations.

## Standard run API

Core's `Mads` type remains the one public application type. Because core must
remain HTTP-independent, `mads-common` implements the static run method through
an extension trait:

```rust
pub trait MadsRunExt {
    fn run<M>() -> impl Future<Output = Result<(), HttpRuntimeError>> + Send
    where
        M: Module;
}

impl MadsRunExt for Mads {
    // ...
}
```

With the trait in the standard prelude, user code calls:

```rust
Mads::run::<AppModule>().await
```

There is no second facade wrapper named `Mads` and no duplicate builder type.
The run extension is available when the HTTP feature is enabled.

`Mads::run`:

1. loads conventional configuration;
2. selects the root module and automatic-HTTP execution mode;
3. builds and validates the scoped application;
4. builds the selected router;
5. applies final application-wide router configuration;
6. starts lifecycle hooks;
7. resolves and binds the configured address;
8. serves with Ctrl-C graceful shutdown;
9. stops lifecycle hooks on every post-start exit path.

`HttpRuntimeError` remains the runtime error envelope. Configuration, module,
provider, route, guard, strategy, server-preflight, CORS, and no-runnable-route
errors use `HttpRuntimeError::Bootstrap(mads_core::Error)`. Existing lifecycle,
bind, serve, and combined operation/shutdown variants remain.

A standard run with no reachable managed route returns a dedicated structured
bootstrap diagnostic. v0.6.0 does not turn this case into an indefinite
lifecycle-only wait.

## Conventional configuration loading

Only `Mads::run` loads conventional sources automatically. It uses the process
current working directory and this order:

1. optional `.env` through `DotenvSource`, used only as an interpolation map;
2. optional `mads.toml` as the ordinary file configuration source;
3. `EnvSource::new("MADS_")` as the final direct override source.

Process variables override dotenv variables during exact `${NAME}`
interpolation, preserving current behavior. Dotenv loading never mutates the
process environment. `MADS_SERVER__PORT`, for example, maps to `server.port`
and overrides TOML.

Both files may be absent. A present file that is unreadable or malformed is a
fatal bootstrap error. No source is searched in parent directories or relative
to `CARGO_MANIFEST_DIR`.

The low-level builder remains completely explicit and does not load files or
process configuration automatically.

Configuration syntax is parsed when present even if a particular capability
is not selected. Capability-specific missing-key and semantic validation runs
only when the scoped application needs that capability. v0.6.0 adds no generic
typed-config requirement API.

## HTTP server configuration

Automatic binding reads:

```toml
[server]
host = "127.0.0.1"
port = 3000
```

Defaults are:

- `server.host = "127.0.0.1"`
- `server.port = 3000`

The host must be a nonempty hostname, IPv4 address, or IPv6 address. The port
must be an integer in `1..=65535`; port zero is rejected for automatic
execution.

v0.6.0 binds one ordinary Tokio TCP listener and uses the existing Axum server
and Ctrl-C shutdown behavior.

Route, dependency, configuration, and CORS preflight completes before
lifecycle startup. Lifecycle hooks start before DNS/address resolution and
binding, preserving existing server ordering. A resolution or bind failure
therefore triggers rollback/shutdown. If that cleanup also fails,
`OperationAndShutdown` retains both errors.

Explicit low-level serving remains:

```rust
serve(application, address).await?;
serve_router(application, raw_router, address).await?;
```

An explicit address is the complete bind override. `server.host` and
`server.port` are ignored for binding and the server decision is
`Overridden`. An explicit address may use port zero. Module scope, CORS,
lifecycle startup, failure rollback, serving, and shutdown behavior are still
applied.

## CORS configuration

CORS is compiled as part of the existing `http` feature. `[server.cors]`
absence disables it at runtime.

An explicit-list configuration is:

```toml
[server.cors]
origins = ["https://app.example.com"]
methods = ["GET", "POST"]
allowed_headers = ["authorization", "content-type"]
exposed_headers = ["x-request-id"]
credentials = false
max_age_seconds = 600
```

Wildcard-capable fields use the scalar string shape:

```toml
[server.cors]
origins = "*"
methods = ["GET", "POST"]
allowed_headers = "*"
exposed_headers = "*"
```

### Shape and defaults

- `origins` is required and is either scalar `"*"` or a nonempty string array.
- `methods` is required and is a nonempty string array.
- Method wildcard is unsupported.
- `allowed_headers` is optional and is either scalar `"*"` or a string array;
  it defaults to an empty list.
- `exposed_headers` has the same shape and default as `allowed_headers`.
- `credentials` defaults to `false`.
- `max_age_seconds` is optional; absence omits the response header and zero is
  valid.
- `origins = ["*"]`, `allowed_headers = ["*"]`, and
  `exposed_headers = ["*"]` are rejected. Wildcard and list forms are
  intentionally different.

The existing environment source is scalar-only. v0.6.0 does not introduce a
CSV, JSON, or delimiter convention for overriding list fields through process
variables.

### Validation

Explicit origins accept canonical HTTP and HTTPS origins consisting of scheme,
host, and optional port. They reject paths, trailing slashes, queries,
fragments, user information, `null`, regexes, and globs. Matching is by exact
origin rather than host suffix.

Methods are validated as HTTP method tokens, normalized to uppercase, and
deduplicated. Header values are validated as HTTP header names and deduplicated
case-insensitively.

When `credentials = true`, wildcard origins, wildcard allowed headers, or
wildcard exposed headers are invalid. MADS diagnoses these combinations before
constructing Tower HTTP middleware so invalid user input cannot trigger a
middleware panic.

Validation errors identify the key, element position when applicable, and
source label without echoing the loaded value.

### Runtime semantics

MADS uses Tower HTTP's standard CORS semantics:

- a valid preflight is answered immediately with an empty `200` response;
- preflight does not enter application guards or handlers;
- a disallowed preflight receives no matching allow headers rather than a
  custom MADS `403` body;
- an actual request continues to the inner application even when its origin is
  disallowed;
- the disallowed actual response lacks matching CORS allow headers, leaving the
  browser to block response access;
- actual requests remain subject to guards and handlers.

CORS is the outermost application layer after generated and native routes are
merged. Allowed-origin responses therefore include CORS headers for normal
responses and application-generated `400`, `401`, `403`, `404`, and `500`
responses.

Documentation must state that CORS is a browser response-access policy, not an
authorization boundary or CSRF defense. Cookie-authenticated applications need
an independent CSRF policy.

## Router composition

`build_router` preserves its existing role and returns a raw generated Axum
router. It does not apply application-wide CORS, allowing users to merge native
routes first.

```rust
let router = build_router(&application)?.merge(native_router);
let router = configure_router(&application, router)?;
```

`configure_router(&application, raw_router)` consumes the complete raw router,
validates relevant HTTP configuration, and applies CORS once as the outermost
layer. It returns a core bootstrap result suitable for in-process service
tests.

`serve(application, address)` builds the generated router and configures it
internally. `serve_router(application, raw_router, address)` configures the
supplied complete raw router internally. Callers either invoke
`configure_router` for direct router use or pass the raw router to
`serve_router`; passing an already configured router to `serve_router` violates
the raw-router API contract and is documented against.

A supplied native router counts as an active low-level HTTP application even
when the scoped MADS route catalog is empty. `configure_router` and
`serve_router` therefore validate and apply configured CORS to native-only
routers. `Mads::run`, which receives no native router, still requires at least
one reachable managed route.

## Lifecycle and migration behavior

The existing lifecycle contract remains:

- all preflight finishes before startup;
- hooks start in registration order;
- startup failure rolls back already-started hooks;
- shutdown runs in reverse order;
- post-start listener and serving errors always attempt shutdown;
- combined operational and shutdown failures preserve both errors.

Standard v0.6.0 startup does not discover or run embedded migrations. Existing
migration registration remains an explicit low-level builder operation. The
v0.6.0 clean-architecture example therefore uses `database.migrate = false`
unless it also demonstrates the low-level migration builder path.

## Determinism and diagnostics

All inventories are sorted before analysis using stable type names and source
locations. Import declaration order is retained where it is user-authored.
Diamond deduplication uses `TypeId`; diagnostic ordering never depends on
linker inventory order or hash iteration order.

New module diagnostics cover:

- missing root metadata;
- multiple module declarations in one namespace;
- duplicate direct imports;
- self-import and import cycles;
- inaccessible cross-module providers;
- restricted/private cross-module providers;
- invalid scoped HTTP dependencies.

HTTP bootstrap diagnostics cover invalid server configuration, invalid CORS,
and a standard application with no runnable route. Existing diagnostic code
ranges remain stable; new codes are allocated without changing the meaning of
existing codes.

No diagnostic, report, `Debug`, or authored assertion message may include a
resolved configuration value. Source labels and configuration keys are safe to
retain.

## Compatibility

- Argument-free unit `#[module]` declarations remain source-compatible.
- Existing global `Catalog`, `RouteCatalog`, guard, and strategy catalog APIs
  remain.
- Existing rootless builder analysis and construction remain complete-catalog.
- Existing explicit configuration remains unchanged.
- Existing `build_router` remains raw and unlayered.
- Existing explicit `serve` remains available and gains final configured
  router behavior.
- Native Axum routing remains a low-level API.
- Public APIs are documented and unsafe code remains forbidden.

Moving `MadsBuilder` out of the standard prelude intentionally narrows the
recommended API without deleting the type or inherent builder functions.

## Documentation and roadmap changes

The release work updates `final_timelinev1.md` so the former v0.5.6 content is
part of one v0.6.0 milestone. Forward-looking references in `/docs`, examples,
importance notes, specifications, and plans are updated where they describe
the future milestone. Historical v0.5.5 behavior remains documented as
shipped; supersession notes are preferred when rewriting history would be
misleading.

`docs/examples/final_application_clean_architecture.md` is the reference for
the module layout and standard run API. Its later-v1 trait-binding,
`Inject<dyn Trait>`, and validation examples remain conceptual and are labeled
accordingly rather than being pulled into v0.6.0.

Standard examples use:

```rust
#[mads::main]
async fn main() -> Result<(), HttpRuntimeError> {
    Mads::run::<AppModule>().await
}
```

Low-level documentation retains builder examples for explicit values,
lifecycle hooks, embedded migrations, custom configuration sources, explicit
addresses, and native routers.

## Verification strategy

### Macro and compile-time tests

- argument-free leaf module;
- module with one and multiple imports;
- imported type must implement the generated module contract;
- unknown/repeated arguments and invalid struct shapes;
- exact facade compilation for the standard `AppModule` and `Mads::run` API;
- facade separation between the standard prelude and `mads::core` builder API.

### Core module and provider tests

- segment-correct namespace ownership;
- nearest nested module ownership;
- nested module is not implicitly imported;
- duplicate namespace and duplicate direct import diagnostics;
- self-cycle, multi-module cycle, and deterministic import-chain diagnostics;
- diamond import edge retention with exactly-once module/provider activation;
- internal private and restricted provider access;
- direct public cross-module access;
- missing direct import and non-transitive import failures;
- unowned provider chain cannot bypass visibility;
- unowned transitive dependency inclusion;
- unreachable invalid providers ignored by rooted analysis;
- rootless complete-catalog compatibility;
- repeated root selection failure;
- retained module graph and provider ownership inspection.

### Scoped common integration tests

- only reachable controllers and routes are registered;
- conflicts are global across reachable modules;
- unreachable invalid routes and guards are ignored;
- guard provider visibility follows module rules;
- per-context strategy lookup;
- one custom strategy overrides built-in JWT only where visible;
- visible duplicate strategy failure and disjoint same-name success;
- unreachable database and JWT requirements do not require configuration.

### Automatic configuration and server tests

- both conventional files absent;
- optional files loaded only from the current working directory;
- malformed or unreadable present files fail safely;
- dotenv is interpolation-only and process interpolation wins;
- `MADS_*` direct override precedence;
- default host and port;
- accepted hostname, IPv4, and IPv6 inputs;
- empty host, invalid host shape, non-integer port, zero, and overflow failure;
- no-runnable-route standard-run failure;
- explicit address ignores server keys and permits port zero;
- all bootstrap checks precede lifecycle startup;
- bind failure triggers shutdown;
- combined operation/shutdown errors retain both failures;
- graceful shutdown preserves existing ordering.

### CORS tests

- absent table disables CORS;
- required origins and methods;
- scalar wildcard versus explicit list shapes;
- rejection of wildcard array elements and method wildcard;
- origin syntax and exact matching;
- method normalization and deduplication;
- case-insensitive header validation and deduplication;
- default credentials, headers, and max age;
- zero max age and absent max-age header;
- credentials/wildcard combinations fail before middleware construction;
- allowed and disallowed preflights;
- preflight bypasses guards and handlers;
- allowed and disallowed actual requests;
- guarded and error responses receive allowed-origin headers;
- generated plus native router layering;
- native-only low-level router CORS;
- `build_router` remains raw;
- direct `configure_router` and internal `serve_router` configuration paths.

### Release gates

The implementation must pass:

```text
cargo fmt --all --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace --all-features
RUSTDOCFLAGS="-D warnings" cargo doc --workspace --all-features --no-deps
```

Workspace line coverage remains at least 85%. Feature-matrix checks cover HTTP
with its CORS dependency, common integrations individually, and the default
facade combination.

## Acceptance criteria

v0.6.0 is complete when:

1. the standard public entry point compiles and runs exactly as
   `Mads::run::<AppModule>().await`;
2. root modules select a deterministic module and provider scope;
3. Rust namespace ownership and direct-import/plain-`pub` visibility are
   enforced without manual registration arrays;
4. unowned dependency chains cannot bypass module boundaries;
5. reachable routes, guards, strategies, and official auto-configurations use
   the same scope;
6. the conventional configuration chain and automatic listener work with the
   approved defaults and lifecycle ordering;
7. CORS validates the approved scalar-wildcard/list contract and wraps the
   complete application router;
8. native-only low-level routers can receive configured CORS;
9. explicit builder, configuration, address, migration, catalog, and native
   router workflows remain available;
10. reports and diagnostics remain deterministic and configuration-value-safe;
11. the former v0.5.6 roadmap is merged into v0.6.0 across maintained
    documentation;
12. all repository quality and coverage gates pass.
