# MADS.rs v0.3 HTTP Route Runtime Design

## Purpose

This specification defines MADS.rs v0.3.0, HTTP and Routing Runtime. It turns
the framework-neutral route and controller contracts introduced in v0.1 into
an executable Axum runtime without adding HTTP dependencies to `mads-core` or
changing the v0.2 provider graph semantics.

The runtime validates the complete application route surface before it creates
an Axum router or opens a TCP listener. Generated registrars invoke controller
trait methods through typed Rust calls; route handler names remain metadata for
inspection and diagnostics only.

## Goals

Version 0.3 must provide:

- application-wide, fail-closed route validation with `MADS030` diagnostics;
- typed controller handler registration with no string-based dispatch;
- Axum 0.8 router generation from the existing route/controller contracts;
- application-scoped controller resolution through the validated v0.2 graph;
- `Path<T>`, `Query<T>`, `Json<T>`, typed `Header<T>`, and native `Request`
  integration;
- basic HTTP response mapping through `HttpError`, `HttpResult<T>`,
  `Created<T>`, and `NoContent`;
- direct Axum extractor, response, router, and Tower-layer escape hatches;
- identical conditional-compilation behavior for methods, metadata, and
  registrars;
- runtime validation of metadata supplied by macros or external integrations;
- explicit and tested HEAD, OPTIONS, route-precedence, trailing-slash, and
  source-location policies;
- a server entry point that validates routes before binding a listener;
- in-process router tests and a complete CRUD-style integration example.

## Non-Goals

Version 0.3 does not include:

- changes to provider selection, dependency ownership, scopes, visibility
  enforcement, or graph construction;
- request-scoped or transient dependency injection;
- automatic trait bindings, qualifiers, or named providers;
- application error normalization, validation, or exception policies reserved
  for v0.7;
- middleware abstraction beyond direct Axum/Tower composition;
- configuration-driven host, port, TLS, or auto-configuration;
- graceful-shutdown policy beyond the basic lifecycle integration required to
  stop a running server;
- HEAD or OPTIONS route attributes;
- wildcard route declarations, parameterized controller prefixes, automatic
  trailing-slash redirects, or legacy Axum colon-path mode;
- Diesel, database, cache, Redis, rate limiting, or CLI route output.

## Crate Boundaries and Dependencies

`mads-core` remains framework-neutral and must not depend on Axum, Tower,
Hyper, HTTP, or `mads-common`.

`mads-common` owns the HTTP runtime. It adds Axum 0.8 with the features needed
for JSON, Tokio serving, and HTTP/1, plus `axum-extra` typed-header support.
Both dependency lines must remain compatible with the workspace Rust 1.85
minimum. `mads-common` re-exports the narrow application-facing types and an
explicit `axum` escape hatch so normal applications do not need manual state or
router wiring.

`mads-common-macros` remains a proc-macro crate. It generates metadata and
typed adapters that refer to public, doc-hidden support APIs in `mads-common`;
it does not depend on or link the Axum runtime directly.

`mads` remains the public facade. With the default `common` feature it exports
the HTTP macros, extractors, responses, server helpers, and relevant prelude
items. The explicit `mads::core::Result` path remains available for framework
and bootstrap operations.

## Runtime Architecture

The runtime follows this sequence:

```text
compile-time route trait
        |
        +-- immutable observability metadata
        +-- typed trait-method registrar
                         |
compiled controller descriptor
        |
        v
complete RouteCatalog
        |
        v
validate every controller and route
        |
        v
convert validated MADS paths to Axum 0.8 syntax
        |
        v
resolve application-scoped controllers
        |
        v
invoke typed registrars and build Router
        |
        v
start lifecycle, bind listener, serve, shut down lifecycle
```

Graph analysis and provider construction still occur in
`MadsBuilder::build().await`. HTTP validation occurs when `build_router` or
`serve` enters the HTTP bootstrap boundary. A route failure may occur after
providers have been constructed, but it must occur before lifecycle startup,
router construction, or listener binding.

## Typed Registration Model

`#[routes]` generates, for every contract, a hidden typed registration method
that knows the declared method signatures and calls the trait method using
fully qualified syntax. Conceptually, an adapter for `UserRoutes::get_user`
performs:

```rust,ignore
let controller = controller.clone();
move |path: Path<i64>| {
    let controller = controller.clone();
    async move { <UserController as UserRoutes>::get_user(&controller, path).await }
}
```

The generated closure captures the application-scoped controller handle. It
does not use `State<AppState>` and does not resolve providers per request.
Controller dependencies remain fields constructed by the v0.2 graph; route
method parameters are exclusively HTTP extractors or other Axum handler
arguments.

`#[controller]` generates one concrete registrar function for the controller.
The function resolves the controller from `ApplicationContext`, then invokes
each declared route trait's hidden registration method. The
`ControllerRouteDescriptor` stores that typed registrar function pointer next
to its metadata.

Trait calls use fully qualified syntax, so two implemented route traits may use
the same method name without ambiguous dispatch. The registrar never reads
`RouteDescriptor::handler()` to select executable code.

Public, doc-hidden adapter types may carry Axum `Router`, validated paths, and
`ApplicationContext` across macro expansions. They are implementation support,
not a stability promise for normal application code.

## Metadata and Registration Relationship

Handler names, trait names, controller names, methods, paths, and source
locations remain immutable metadata. Registrars are executable function
pointers. These two roles stay separate so catalog inspection never invokes a
handler and runtime dispatch never searches strings.

Generated registrars consume paths produced by runtime validation rather than
registering unchecked raw descriptor paths. Metadata constructors remain
public because proc macros expand in downstream crates, and integration crates
may construct descriptors manually. Such metadata receives exactly the same
validation as macro output.

Executable registrar code is trusted Rust code linked into the application;
its accompanying metadata is not trusted merely because a constructor was
called.

## Fail-Closed Validation

`RouteCatalog::validate()` remains the application-wide entry point and is
extended to validate descriptor integrity before conflict detection. Validation
uses deterministic controller, contract, and route ordering and returns
`MADS030` for the first invalid route condition with related diagnostics where
another declaration is involved.

Validation checks:

- controller type name is non-empty;
- one controller `TypeId` has exactly one descriptor identity;
- one controller type name does not refer to different `TypeId` values;
- controller contracts are non-empty and have non-empty trait names;
- duplicate contract descriptors within a controller are rejected;
- every contract has at least one active route;
- HTTP method is one of the closed `HttpMethod` variants;
- prefix, endpoint path, and full path independently satisfy the route grammar;
- `full_path` exactly equals the canonical join of `prefix` and endpoint path;
- source file is non-empty and line and column are non-zero;
- duplicate or structurally equivalent method/path descriptors are rejected
  within and across controllers;
- each controller has a typed registrar.

Structural conflict identity treats each `:parameter` segment as a wildcard,
so `GET /users/:id` conflicts with `GET /users/:user_id`. A conflict diagnostic
identifies both controller names and includes both source locations. No Axum
API is called when validation fails.

The route grammar continues to reject query strings, fragments, percent
encoding, backslashes, whitespace, control characters, empty segments, `.` or
`..` segments, repeated parameter names, parameters embedded in static
segments, wildcard segments, parameterized prefixes, and non-root trailing
slashes.

## Path Translation and Routing Policy

MADS preserves its documented `/:id` contract syntax. After validation, the
adapter translates complete parameter segments to Axum 0.8 `/{id}` syntax.
The adapter never disables Axum's current path checks and never passes a raw
MADS colon path to `Router::route`.

The HTTP policies are:

- a GET route also handles HEAD; Axum removes the response body;
- v0.3 does not synthesize OPTIONS handlers;
- unsupported methods return Axum's `405 Method Not Allowed` response with its
  `Allow` header, including HEAD when GET exists;
- static and dynamic paths may coexist, and the static route takes precedence;
- `/users` and `/users/` are distinct request paths;
- declarations ending in `/` are rejected unless the entire route is `/`;
- v0.3 performs no trailing-slash redirects or normalization;
- a missing path uses Axum's default `404 Not Found` response;
- registration is deterministic and does not rely on inventory iteration
  order.

Tests assert these policies against the constructed Axum router rather than
only against catalog metadata.

## Conditional Compilation and Attribute Identity

For each route method, `#[routes]` copies all `cfg` and `cfg_attr` attributes
onto:

- the retained trait method;
- its metadata entry;
- its generated typed registration statement.

Consequently a route excluded from the active build is absent from the trait,
catalog, and router together. Feature-matrix consumer crates prove both the
enabled and disabled builds.

The endpoint verb itself must be a direct `get`, `post`, `put`, `patch`, or
`delete` attribute. Placing a verb inside `cfg_attr` is rejected with a focused
compile diagnostic; callers use a direct verb plus `#[cfg(...)]` instead.
Other `cfg_attr` uses are preserved and copied.

For v0.3, endpoint attributes continue to be recognized by their final path
segment. This preserves unqualified prelude use, `mads::get`, direct
`mads_common::get`, and renamed facade/common dependencies. Compile tests cover
all supported dependency paths. Namespace narrowing is not introduced as an
incidental breaking change in this milestone.

## Extractors and Native Axum Escape Hatch

`mads-common` exports:

```rust,ignore
pub use axum::extract::{Path, Query, Request};
pub use axum::Json;
pub use axum_extra::TypedHeader as Header;
pub use axum_extra::headers;
```

`Header<T>` retains the typed-header contract from the `headers` crate.
Extractor rejection behavior remains Axum/axum-extra behavior in v0.3; MADS
does not reimplement deserialization or rejection mapping.

Generated handlers preserve declared argument order and types. This permits
native Axum extractors as an escape hatch. Axum's handler trait remains the
source of truth for extractor ordering, body-consuming extractors, `Send`, and
arity constraints; compile tests ensure the generated adapter produces useful
Rust diagnostics when a signature is not a valid Axum handler.

The HTTP runtime publicly re-exports Axum under `mads::common::axum` so callers
can use `Router`, `IntoResponse`, native extractors, middleware, and Tower
composition without MADS wrappers.

## Basic Response Model

Route handlers may return any type accepted by Axum's `IntoResponse`, including
native `Result<T, E>` where both branches satisfy Axum response requirements.

MADS additionally provides:

```rust,ignore
pub type HttpResult<T> = std::result::Result<T, HttpError>;

pub struct Created<T>(pub T);
pub struct NoContent;
```

`Created<T>` delegates response conversion to `T` and then sets status 201.
`NoContent` returns status 204 with an empty body.

`HttpError` is an HTTP-delivery error, distinct from `mads_core::Error`. Its
initial public constructors are `bad_request`, `not_found`, `conflict`, and
`internal`. The first three expose the supplied safe message. `internal`
returns a generic client message and does not serialize or display a stored
source error in the response.

All `HttpError` variants produce JSON with this stable v0.3 shape:

```json
{
  "error": {
    "code": "not_found",
    "message": "user was not found"
  }
}
```

The status/code mapping is 400/`bad_request`, 404/`not_found`,
409/`conflict`, and 500/`internal`. Broader application error conversion,
validation payloads, custom error registries, and domain-error policies remain
reserved for v0.7.

The default prelude exports `HttpError`, `HttpResult`, `Created`, `NoContent`,
`Path`, `Query`, `Json`, `Header`, and `Request`. It does not export
`mads_core::Result` under the bare name once `HttpResult` is present; framework
code uses `mads::core::Result` explicitly.

## Router and Server APIs

The primary router API is:

```rust,ignore
pub fn build_router(application: &Mads) -> mads_core::Result<axum::Router>;
```

It validates the complete route catalog, resolves every registered controller,
and invokes typed registrars. It returns a state-complete `Router<()>` that can
be exercised in-process or composed with native Axum/Tower APIs. It does not
start lifecycle hooks or bind a listener.

The primary server API is conceptually:

```rust,ignore
pub async fn serve(
    application: Mads,
    address: impl tokio::net::ToSocketAddrs,
) -> Result<(), HttpRuntimeError>;
```

`serve` performs operations in this order:

1. validate all route metadata and build the router;
2. start application lifecycle hooks;
3. bind the TCP listener;
4. serve the router with basic shutdown handling;
5. shut down application lifecycle hooks.

If lifecycle startup succeeds but binding or serving fails, `serve` still
attempts lifecycle shutdown. Failure reporting preserves the operational error
as primary and retains a shutdown failure as related context.

`HttpRuntimeError` distinguishes route/bootstrap diagnostics, lifecycle
failures, bind failures, serving failures, and combined operational/shutdown
failures. It implements `std::error::Error` and must preserve
`mads_core::Error` as a source rather than flattening `MADS030` text.

This API guarantees invalid application routes do not construct an Axum router,
start lifecycle hooks, or open a listener. Host/port configuration and
auto-binding are deferred to v0.5.

## Failure and Panic Policy

Invalid route metadata, controller resolution, and route conflicts return
errors. They must not panic.

Axum route construction can panic for invalid syntax or overlapping handlers.
MADS prevents those inputs through validation, canonical ordering, and
conflict detection. A test encloses router construction for malformed manual
metadata and proves the adapter returns `MADS030` before reaching Axum.

Generated registrars use no `unwrap` or `expect` on request or bootstrap data.
Internal assertions are permitted only for invariants already proven in the
same function and must carry a stable explanatory message.

Extractor rejection and response conversion follow Axum behavior. Handler
errors use `HttpError` or a caller-provided `IntoResponse` error and never pass
through the provider graph.

## Testing Strategy

Implementation follows red-green-refactor. Each execution task begins with a
focused failing test and ends with the affected crate's test and Clippy gates.

Required test layers are:

- proc-macro unit tests for generated typed registration, UFCS dispatch,
  copied `cfg`/`cfg_attr`, path translation inputs, and argument forwarding;
- trybuild pass/fail fixtures for renamed dependencies, conditional routes,
  verbs nested in `cfg_attr`, malformed signatures, and native extractors;
- `mads-common` unit tests for descriptor integrity, canonical joins, path
  translation, deterministic ordering, response wrappers, and error JSON;
- isolated integration-test binaries for cross-controller conflicts and both
  source locations in `MADS030`;
- router-level request tests using `tower::ServiceExt::oneshot` for all five
  CRUD verbs, path/query/JSON/header/request extraction, native Axum
  extractors, `Created`, `NoContent`, and `HttpResult`;
- routing-policy tests for GET-to-HEAD body removal, OPTIONS returning 405 with
  `Allow`, static-over-dynamic precedence, strict trailing slashes, and 404;
- a same-method-name test across two traits proving typed, unambiguous calls;
- feature-matrix consumer builds proving a conditional route appears and
  disappears from method availability, metadata, and router together;
- a server preflight test proving invalid routes run no lifecycle hook and
  perform no bind attempt;
- facade tests proving default-feature exports and no-default core-only builds;
- documentation tests showing a complete in-process CRUD router and server
  bootstrap.

The final milestone gates are:

```text
cargo fmt --all --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace --all-features
RUSTDOCFLAGS="-D warnings" cargo doc --workspace --all-features --no-deps
cargo test --workspace --all-features --doc
cargo llvm-cov --workspace --all-features --ignore-filename-regex '(^|/)tests/ui/' --fail-under-lines 85
```

## Documentation and Versioning

Public crate and README documentation must replace the v0.2 statement that
HTTP execution is reserved. Documentation includes:

- the route/controller programming model;
- extractor and response imports;
- in-process router testing;
- explicit route and HTTP method policies;
- native Axum/Tower escape hatches;
- the distinction between `HttpResult` and `mads::core::Result`;
- the server lifecycle and validation-before-bind guarantee.

The workspace version advances from 0.2.0 to 0.3.0 only after every acceptance
criterion and verification gate passes.

## Acceptance Criteria

Version 0.3 is complete only when all of the following are true:

1. GET, POST, PUT, PATCH, and DELETE controller routes receive real Axum
   requests and invoke the correct typed trait methods.
2. Standard controller routes require neither manual `State<AppState>` nor a
   manual Axum router wiring list.
3. Two traits with the same handler method name dispatch without ambiguity.
4. A conflict across different controllers returns `MADS030`, reports both
   route locations, and occurs before router construction, lifecycle startup,
   or listener binding.
5. Invalid manually constructed metadata returns `MADS030` rather than
   panicking inside Axum.
6. Conditional routes appear and disappear with their trait methods, metadata,
   and registrars in the feature matrix.
7. MADS `/:parameter` paths execute correctly on Axum 0.8 without disabling
   Axum path validation.
8. `Path`, `Query`, `Json`, typed `Header`, `Request`, and at least one native
   Axum extractor work through generated adapters.
9. `Created`, `NoContent`, successful `HttpResult`, and every `HttpError`
   status/JSON mapping are covered by request tests.
10. HEAD, OPTIONS, static/dynamic precedence, trailing slash, 404, 405, and
    `Allow` behavior match the explicit policies in this specification.
11. `build_router` permits in-process testing and direct Axum/Tower
    composition.
12. `serve` validates before binding and integrates application startup and
    shutdown lifecycle hooks.
13. `mads-core` has no HTTP-specific dependency or semantic change.
14. The facade and prelude expose the v0.3 common path while core-only builds
    remain supported.
15. All formatting, lint, test, rustdoc, doctest, and 85 percent coverage gates
    pass on Rust 1.85-compatible dependencies.
