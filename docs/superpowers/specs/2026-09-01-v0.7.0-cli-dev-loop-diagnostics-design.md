# MADS v0.7.0 CLI, Dev Loop, and Diagnostics Design

**Status:** Approved design, pending implementation planning
**Target:** MADS v0.7.0-beta.1, then v0.7.0 stable
**Date:** 2026-09-01

## Context

MADS v0.6.0 provides rooted modules, deterministic provider analysis, scoped
HTTP metadata, conventional configuration loading, auto-configuration reports,
and `Mads::run::<AppModule>()`. The CLI currently provides basic help/version,
the legacy `foundation` output, and database migrate/rollback/status commands.
It cannot inspect the selected user's application because the CLI process does
not contain that application's inventory or root module.

The previous roadmap assigned input validation, standard REST errors, and
typed configuration to v0.7, while postponing the CLI and diagnostics to v0.8.
The revised release order makes a complete development CLI the v0.7 goal.
Input validation and other non-blocking REST/configuration work move to v0.8.

The central architectural constraint is that app-aware commands must inspect
the application compiled by the user without running normal application
startup. MADS will solve this with a short-lived child application process and
a private inspection mode in the standard `Mads::run::<AppModule>()` path.

## Release contract

`0.7.0-beta.1` contains the complete v0.7 feature set. The path from beta.1 to
stable is limited to testing, bug fixes, documentation corrections, and release
verification. Stable v0.7 does not add features omitted from beta.1.

v0.7 includes:

- the complete CLI command surface described below;
- the built-in development watcher and process supervisor;
- app-aware route, graph, and doctor inspection;
- self-contained PostgreSQL migration generation;
- only the diagnostic, configuration, and metadata changes needed by the CLI.

v0.8 receives:

- `#[derive(Input)]`, validators, and deserialize/validate/handler integration;
- structured validation responses;
- expanded standard HTTP application errors;
- automatic Diesel-to-HTTP error mapping;
- generic typed configuration and dedicated secret-safe value APIs;
- broader opaque trait-bound and compiler diagnostic improvements;
- JSON or other machine-readable CLI output.

## Goals

- Make `mads run` and `mads dev` the standard local execution workflow.
- Make routes, dependency selection, and auto-configuration explainable before
  the application starts.
- Preserve Cargo's package and binary selection behavior.
- Ensure framework inspection does not construct providers, start lifecycle
  hooks, connect to PostgreSQL, run migrations, bind sockets, or serve traffic.
- Generate reviewable, reversible migrations from split Diesel schema files
  and live PostgreSQL state without requiring an external Diesel executable.
- Produce deterministic, actionable human-readable diagnostics.
- Support Linux, macOS, and Windows in beta.1.

## Non-goals

v0.7 does not add:

- request input derivation or validators;
- new standard HTTP response errors or automatic persistence error mapping;
- a general typed configuration API;
- JSON or stable machine-readable CLI output;
- hot module replacement or in-process Rust code swapping;
- arbitrary low-level builder inspection;
- static source-code analysis as a replacement for compiled application
  metadata;
- defaults, indexes, checks, triggers, or complete foreign-key policy synthesis
  in schema diff generation;
- automatic application of generated migrations;
- an external `cargo-watch` or Diesel CLI dependency.

## Command surface

The v0.7 CLI is:

```text
mads dev [--package <package>] [--bin <bin>] [-- <app-args>...]
mads run [--package <package>] [--bin <bin>] [-- <app-args>...]
mads routes [--package <package>] [--bin <bin>]
mads graph [--package <package>] [--bin <bin>]
mads doctor [--package <package>] [--bin <bin>]
mads db generate [--package <package>]
mads db migrate [--package <package>]
mads db rollback [--package <package>]
mads db status [--package <package>]
```

`-p` aliases `--package`. Arguments after `--` are passed unchanged to the
application for `run` and `dev`. When selectors are absent, Cargo chooses the
target or reports its normal ambiguity. The CLI must not invent a different
default-target algorithm.

The legacy `mads foundation` command is removed. `mads doctor` supersedes it.
`mads db generate <name>` and `--diff-schema` do not exist; generation always
means one complete current schema-to-database diff with an automatic name.

Human-readable deterministic output is the only v0.7 output contract. Internal
wire serialization does not make JSON a public CLI contract.

## Cargo project and target resolution

The CLI resolves the active Cargo workspace and selected package through Cargo
metadata. It passes `--package` and `--bin` to Cargo rather than independently
reimplementing target selection. The selected package root is also the base for
`mads.toml`, optional `.env`, migrations, and Rust schema discovery.

Build commands use Cargo's structured artifact messages to identify the exact
binary path. Cargo and rustc output is streamed without MADS rewriting compiler
diagnostics. A build failure is a CLI operational failure, not a MADS graph
diagnostic.

Before app-aware inspection, metadata must show an inspection-capable MADS v0.7
dependency. An incompatible framework version fails before the application is
launched. A second runtime handshake detects source overrides or other protocol
mismatches that metadata alone cannot establish.

## Private application inspection

### Process model

App-aware commands use two processes:

```text
mads CLI parent
  -> build selected application binary
  -> launch one short-lived child in inspection mode
  -> receive structured report
  -> render and exit
```

The child is not a second server. It exits before normal application startup.
Normal `mads run` and `mads dev` execution does not enable inspection mode.

### Entry interception

The private request contains a protocol version, command kind, and per-request
token. `Mads::run::<AppModule>()` checks for a complete valid request before
loading normal runtime state. An incomplete or forged environment toggle is not
enough to enter inspection mode.

For a valid request, the standard run path:

1. acknowledges the protocol version and request token;
2. loads conventional configuration for read-only validation;
3. creates a rooted builder for `AppModule`;
4. supplies the same server and CORS auto-configuration inputs as normal run;
5. performs graph analysis without provider construction;
6. scopes routes, guards, strategies, and HTTP metadata to the module graph;
7. evaluates inspection-safe configuration and auto-configuration reports;
8. writes one owned response envelope;
9. exits without entering normal build, lifecycle, database, or server paths.

The report transport is private and versioned. It must tolerate unrelated
application stdout/stderr without confusing logs with protocol data. The parent
sets a handshake deadline and a completion deadline. Version mismatch,
malformed output, child failure, or timeout terminates the child and becomes an
actionable MADS CLI diagnostic.

### Supported entry point and side-effect boundary

v0.7 supports binaries that enter through `Mads::run::<AppModule>()`. A binary
that does not reach the inspection hook receives an unsupported-entry-point
diagnostic after the parent terminates it. Arbitrary low-level builder startup
is not inferred or executed.

The side-effect guarantee covers MADS behavior: inspection does not construct
providers, execute lifecycle hooks, connect to PostgreSQL, run migrations, bind
a listener, or serve requests. Cargo build scripts and arbitrary user code run
before `Mads::run` cannot be sandboxed. Such code is outside the standard
entry-point contract and this limitation must be documented.

## Inspection reports

All records are owned and sorted before serialization so parent output does not
depend on inventory order, map iteration order, or process timing.

### Routes report

Each route record contains:

- HTTP method;
- complete path after route prefix composition;
- route trait and handler identity;
- controller identity;
- source location;
- effective guard-active state.

The renderer uses a stable method/path/controller ordering. Route conflicts or
invalid metadata include every safely recoverable route, followed by structured
diagnostics, and exit with failure.

### Graph report

The graph report contains:

- the root module and direct-import tree;
- selected providers and dependency edges;
- provider owner module;
- provider origin;
- visibility;
- selection or auto-configuration state;
- deterministic construction order when valid.

Invalid applications retain the partial graph and diagnostics. The renderer
does not discard useful graph evidence because construction would fail.

### Doctor report

Doctor groups checks into:

- configuration;
- module graph;
- providers;
- routes;
- guards and strategies;
- server and CORS;
- auto-configuration.

Every check is one of `PASS`, `SKIPPED`, `OVERRIDDEN`, or `FAILED`. Failures
carry MADS diagnostics and recovery suggestions. Doctor does not connect to
PostgreSQL; database auto-configuration is evaluated from metadata and
configuration presence only.

Generic configuration checks expose required-key presence, winning source, and
validation status, not raw values. Safe non-secret framework facts may be
rendered by their dedicated checks, but generic configuration dumping is not a
v0.7 feature.

## `mads run`

`mads run` builds the selected binary, executes that artifact directly, streams
application output, forwards arguments after `--`, forwards termination, and
preserves the application's exit result. Framework startup prints a concise
server and route summary after preflight and before serving.

CLI-owned failures before application execution follow CLI exit semantics. Once
the application starts, its own exit status remains authoritative.

## `mads dev`

### Watch set

The built-in cross-platform watcher observes:

- Rust sources in the selected workspace/package and local path dependencies;
- relevant `Cargo.toml` manifests and `Cargo.lock`;
- `mads.toml` and `.env`;
- migration directories;
- `src/schema.rs` and recursive `src/schema/**/*.rs` files.

Generated build output, VCS data, editor temporary files, and the Cargo target
directory are excluded. Events are normalized and debounced into one change
batch before classification.

### Rebuild and restart policy

Rust, Cargo, schema, and embedded-migration changes request a Cargo incremental
build. MADS relies on Cargo's dependency graph and incremental cache; it does not
attempt source-level partial linking or hot swapping.

Changes limited to `.env` or `mads.toml` restart the last successful binary
without invoking Cargo. A batch containing both config and build-relevant files
uses the build path once.

The last successful application remains alive while a replacement compiles. On
success, the supervisor gracefully stops the old child and starts the newly
built artifact. On failure, Cargo/rustc output is shown unchanged and the old
child remains alive. If the initial build fails, no application starts, but the
watcher remains active and retries after a relevant change.

Termination must clean up the active application and any build process on
Linux, macOS, and Windows. Repeated events during a build schedule at most one
follow-up build using the newest observed state.

## Database commands

Existing `migrate`, `rollback`, and `status` retain their current configuration,
redaction, and PostgreSQL behavior.

### Schema discovery

`mads db generate` loads both `src/schema.rs` and every Rust source file below
`src/schema/`, sorted by normalized relative path. It extracts and merges
`diesel::table!` declarations. This allows one schema module or table modules
such as `schema/user.rs` and `schema/comment.rs`.

Duplicate table identities, contradictory columns, unsupported table syntax,
or unknown PostgreSQL type mappings are hard failures with file-aware
diagnostics. The command produces no partial SQL when schema interpretation is
ambiguous. An external Diesel CLI is never invoked.

### Configuration and live snapshot

Generation uses the existing database CLI chain exactly:

1. selected package root;
2. optional `.env`;
3. required `mads.toml`;
4. `MADS_*` environment overrides;
5. `database.url`.

The generator connects to PostgreSQL and captures the supported live table,
column, type, nullability, and primary-key state before planning either file.
Credentials and raw database URLs must not appear in normal, debug, or error
output.

### Supported diff

The v0.7 planner supports:

- create and drop table;
- add and drop column;
- column type changes;
- nullability changes;
- declared primary keys when creating tables;
- inverse SQL derived from the captured live state.

`up.sql` transforms the captured supported state toward the Rust schema.
`down.sql` reverses the generated supported operations toward the captured
state. Operations are dependency-ordered and identifiers are quoted rather than
interpolated as raw SQL.

Defaults, indexes, checks, triggers, exact foreign-key policies, risky casts,
and adding non-null columns to populated tables are not silently invented. The
command emits terminal warnings and review comments where manual SQL may be
required. If unsupported metadata makes a safe supported operation impossible
to express, generation fails without creating files.

### Output and atomicity

When differences exist, the final path is:

```text
migrations/<timestamp>_schema_diff/
  up.sql
  down.sql
```

The timestamp is a sortable UTC value. A collision fails rather than
overwriting an existing path. Parsing, database inspection, planning, and
complete file content generation happen before publication of the final
directory. Temporary artifacts are cleaned after failure.

No differences return success, print that the schema is current, and create no
files. Generated SQL is always review-required and never automatically applied.

## Diagnostics and exit behavior

The existing diagnostic model gains read-only access to its stable code, title,
message, subject, source location, suggestions, and related diagnostics. These
fields feed owned inspection records and the CLI renderer. Existing diagnostics
remain the basis for graph, route, configuration, and auto-configuration
failures; new stable categories cover only CLI-specific failure modes:

- Cargo project, package, and binary selection;
- incompatible or unsupported inspection entry points;
- protocol, child, and timeout failures;
- watcher and process supervision;
- schema discovery and parsing;
- PostgreSQL catalog inspection;
- migration planning and publication safety.

Cargo and rustc diagnostics pass through unchanged. MADS-owned preflight and
runtime diagnostics use the structured human renderer.

For CLI-owned commands:

- `0` means success, including a no-diff database result;
- `1` means build, inspection, validation, or operational failure;
- `2` means invalid CLI syntax or arguments.

For `mads run`, the executed application's exit status is preserved after a
successful launch. `mads dev` remains active through rebuild failures and exits
when explicitly terminated or when the supervisor itself cannot continue.

## Crate boundaries

### `mads-core`

Core remains independent of HTTP, PostgreSQL, the CLI, and wire serialization.
It owns diagnostic accessors, deterministic owned graph snapshots, and the
pre-construction analysis surfaces needed by common.

### `mads-common`

Common owns the standard HTTP run path and therefore owns the hidden inspection
hook. Under the HTTP feature it owns private versioned protocol records and
converts core analysis plus scoped routes, guards, strategies, server/CORS, and
auto-configuration data into one response. Cross-crate protocol items are
public only as `#[doc(hidden)]` implementation details and have no public
stability promise.

### `mads-cli`

The CLI owns parsing, Cargo metadata and builds, process supervision, the
watcher, renderers, schema source parsing, PostgreSQL catalog reads, diff
planning, SQL generation, and migration directory publication. It may depend
directly on the internal common protocol types; neither core nor common depends
on the CLI.

### Facade and macros

The `mads` facade continues to expose the standard application experience and
`Mads::run`. Macro crates change only if an approved report field is not already
captured. Existing route, guard, provider, and module source locations are
reused instead of building a parallel registry.

The dependency direction remains:

```text
mads-cli ------> mads-common ------> mads-core
application ---> mads facade -----> mads-common + mads-core
```

No new workspace crate is introduced.

## Testing strategy

Implementation proceeds in test-first increments.

Unit coverage includes command parsing, selectors, argument forwarding,
deterministic rendering, event normalization, debounce/classification, schema
merging, diff ordering, inverse planning, quoting, and SQL rendering.

Fixture applications cover:

- a standard single-package application;
- Cargo workspaces with multiple packages and binaries;
- split schema files;
- invalid module/provider graphs;
- route conflicts;
- incompatible framework and protocol versions;
- an entry point that never reaches `Mads::run`;
- inspection child crashes and timeouts.

Inspection fixtures use marker providers, lifecycle hooks, database hooks, and
bind checks to prove that inspection reaches none of them.

Watcher/process tests prove config-only restart, Cargo incremental rebuild
selection, last-good-process behavior after compilation failure, event
coalescing, argument forwarding, and child cleanup. Platform-specific process
abstractions are exercised on Linux, macOS, and Windows CI.

Real PostgreSQL integration tests cover every supported operation. For each
case, tests capture the initial database shape, generate both files, apply up,
verify the desired supported shape, apply down, and verify restoration. They
also cover no-diff behavior, redaction, warnings, collision refusal, and cleanup
after failure.

The release runs the repository's formatting, Clippy, workspace/all-feature,
documentation, feature-combination, and MSRV 1.85 gates. Beta.1 is not cut until
the complete command matrix passes. Stable promotion reruns the same matrix and
contains no additional feature work.

## Resolved decisions

- The CLI uses a short-lived application child, not a dedicated inspection
  binary or static metadata file.
- v0.7 supports the standard `Mads::run::<AppModule>()` path only.
- `mads foundation` is removed in favor of `mads doctor`.
- Migration generation has no user-supplied name and always computes the full
  diff.
- Split schema files are first-class inputs.
- The generator is self-contained and PostgreSQL-only.
- Doctor is offline with respect to application runtime and the database.
- Dev mode uses Cargo incremental compilation and config-only restart, not HMR.
- MADS diagnostics are structured; Cargo/rustc output is unchanged.
- Output is human-readable only in v0.7.
- Beta.1 contains all v0.7 features; stable adds none.

There are no open design questions before implementation planning.
