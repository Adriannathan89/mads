# MADS.rs v0.4.0 Diesel-first Persistence Specification

**Status:** Approved for implementation
**Milestone:** v0.4.0 — Diesel-first Persistence
**Roadmap source:** `final_timelinev1.md`
**Previous milestone:** `docs/superpowers/specs/2026-08-21-v0.3-http-runtime-design.md`

## Problem statement

MADS.rs v0.3 can construct an application graph and execute typed HTTP routes,
but a real CRUD service still has to choose and initialize a database pool,
move synchronous Diesel work off the async runtime, run migrations, inject the
database into repositories, and coordinate shutdown manually. That plumbing is
exactly the common-path infrastructure MADS is intended to own.

Version 0.4.0 adds an explicit PostgreSQL/Diesel persistence capability to
`mads-common`. It must be complete enough to run a real CRUD slice while
preserving the existing architecture:

- `mads-core` remains free of Diesel, PostgreSQL, pools, and migration
  semantics;
- `Database` is one application-scoped provider shared through the existing
  dependency graph;
- native Diesel query types and DSL remain available;
- synchronous Diesel work never blocks a Tokio worker thread;
- pool readiness, optional startup migrations, and pool closure participate in
  the MADS lifecycle;
- the CLI can apply, revert, and inspect file-based migrations; and
- v0.5 remains responsible for deciding automatically when database
  infrastructure should be provisioned.

## Goals

1. Add a documented `mads_common::database` boundary backed by PostgreSQL,
   Diesel 2.2, and `deadpool-diesel`.
2. Parse and validate the v0.4 database configuration contract:

   ```toml
   [database]
   url = "${DATABASE_URL}"
   pool_size = 10
   migrate = true
   ```

3. Add generic, optional project-root `.env` loading and exact `${NAME}`
   interpolation to `mads-core`, so database, Redis, and later integrations can
   share one secret-safe configuration pipeline.
4. Provide a cheap-to-clone `Database` handle whose `run` method executes
   native synchronous Diesel work on `deadpool-diesel`'s blocking worker.
5. Normalize pool acquisition, blocking interaction, Diesel query, and
   migration failures behind a stable MADS-owned database error surface.
6. Support embedded migrations programmatically and at application startup.
7. Add `mads db migrate`, `mads db rollback`, and `mads db status` using
   file-based Diesel migrations.
8. Prove repository injection and complete create/list/get/update/delete
   behavior against a real PostgreSQL service in CI.
9. Release all workspace crates as 0.4.0 with updated public documentation.

## Non-goals

The following are deliberately outside v0.4.0:

- automatic detection of a `Database` requirement;
- automatic database provider registration or custom-provider back-off;
- auto-configuration inspection states (`ACTIVE`, `SKIPPED`, `OVERRIDDEN`,
  `FAILED`);
- MySQL, SQLite, or a backend-generic public `Database` type;
- a MADS query language, repository generator, or schema generator;
- a transaction wrapper API; callers may use Diesel transactions inside
  `Database::run`;
- trait bindings such as `#[repository(as = RepositoryPort)]`;
- automatic conversion of database errors into `HttpError`;
- request-scoped connections or transactions;
- migration creation, redo, or destructive all-down commands;
- secret storage, encrypted secret management, or arbitrary/embedded template
  interpolation;
- v0.5 modules/auto-configuration, v0.7 validation/errors, or v0.8 diagnostics
  and development commands.

## Constraints

- The workspace remains Rust edition 2024 with MSRV Rust 1.85.0.
- `mads-core` must have no normal dependency on Diesel, `deadpool-diesel`,
  `diesel_migrations`, PostgreSQL client libraries, or `mads-common`.
- All crate source keeps `#![forbid(unsafe_code)]`; public APIs remain fully
  documented under `#![deny(missing_docs)]`.
- Diesel is pinned to `=2.2.12` and `diesel_migrations` to `=2.2.0`. Diesel
  2.3 requires Rust 1.86 and is incompatible with the workspace MSRV.
- `deadpool-diesel` is pinned to `=0.6.1` with only `postgres` and
  `rt_tokio_1` enabled.
- `toml` is pinned to `=0.8.23` for file configuration without moving the
  workspace to a newer MSRV.
- `dotenvy` is pinned to `=0.15.7`; its MSRV is below the workspace's Rust
  1.85.0 floor.
- `.env` parsing must not mutate the process environment. Rust 2024 makes
  process-environment mutation unsafe, and the workspace forbids unsafe code.
- PostgreSQL is the only v0.4 backend. The API must not imply that other
  backends already work.
- Configuration values can be secrets: MADS-owned `Debug` output and
  diagnostics never print a loaded value, database URL, or interpolated secret.
- Existing v0.3 HTTP behavior and core-only builds remain unchanged.
- Every new public type, method, error variant, facade export, and CLI command
  has tests and documentation.
- No implementation task may lower the 85% line coverage gate.

## Approaches considered

### Chosen: synchronous Diesel through `deadpool-diesel`

`deadpool-diesel` owns a PostgreSQL pool and runs each closure passed to
`interact` on a blocking worker. `Database::run` can therefore accept ordinary
Diesel 2.2 `QueryResult<T>` closures exactly like the target API in the v1
design while presenting an async MADS method to repositories. This is the
smallest adapter that preserves both native Diesel DSL and Tokio correctness.

### Chosen: parse `.env` into an interpolation map

`ConfigBuilder` loads explicitly registered `DotenvSource` files into a
temporary variable map, overlays the Unicode process environment, merges its
normal configuration sources, and resolves exact whole-value `${NAME}`
placeholders. It never calls `set_var`, so configuration construction is
deterministic, safe under Rust 2024, and usable concurrently. This keeps
`.env` support generic: a future `redis.url = "${REDIS_URL}"` uses the same
pipeline without adding Redis-aware behavior to `mads-core`.

### Rejected: mutate the process environment with `.env`

Calling a convenience loader that installs `.env` values globally introduces
cross-test races, makes precedence depend on process history, and requires an
unsafe operation under Rust 2024. The v0.4 API therefore parses files without
changing global state.

### Rejected for v0.4: `diesel-async`

`diesel-async` is viable, but it changes connection types and requires queries
inside `Database::run` to be awaited. That diverges from the existing
`Database::run(move |conn| native_diesel_query(conn)).await` design and adds a
second Diesel execution model before the synchronous baseline is proven.

### Rejected for v0.4: Diesel `r2d2` plus hand-written `spawn_blocking`

This can work, but MADS would have to implement blocking-task dispatch,
connection acquisition timing, panic/cancellation mapping, and shutdown
coordination itself. `deadpool-diesel` already owns that boundary and exposes a
pool close operation, so duplicating it provides no v0.4 value.

## Crate and dependency boundaries

```text
application repository
        |
        v
 mads-common::Database
        |
        +--> deadpool-diesel (pool + blocking interaction)
        |
        +--> Diesel 2.2 / PgConnection / native DSL
        |
        +--> diesel_migrations (embedded and file sources)
        |
        v
    PostgreSQL

mads-core
  application graph + Config + lifecycle contracts only
  no database dependency or database-specific behavior
```

The workspace dependencies added for v0.4 are:

```toml
deadpool-diesel = { version = "=0.6.1", default-features = false, features = ["postgres", "rt_tokio_1"] }
diesel = { version = "=2.2.12", default-features = false, features = ["postgres", "32-column-tables"] }
diesel_migrations = { version = "=2.2.0", default-features = false, features = ["postgres"] }
dotenvy = "=0.15.7"
toml = "=0.8.23"
```

`mads-common` owns the first three dependencies. `mads-core` uses only `toml`
and `dotenvy` to implement generic file configuration and interpolation.
Application crates can use the re-exported Diesel and migration crates without
declaring a second version.

## File structure

```text
crates/mads-core/src/config.rs
    ConfigSource, MapSource, EnvSource, scalar TomlSource, DotenvSource,

crates/mads-common/src/database/

```

Each database file has one responsibility. HTTP route code remains in its
existing modules, and no persistence logic enters the route adapter.

## Configuration contract

### Generic TOML and dotenv sources

`mads_core::TomlSource` implements the existing synchronous `ConfigSource`
contract:

```rust
pub struct TomlSource { /* path */ }

impl TomlSource {
    pub fn file(path: impl Into<std::path::PathBuf>) -> Self;
}
```

`TomlSource::load` reads the file and recursively flattens scalar TOML keys:

```toml
[database]
url = "postgres://host/database"
pool_size = 10
migrate = false
```

becomes:

```text
database.url       = postgres://host/database
database.pool_size = 10
database.migrate   = false
```

Strings, integers, floats, and booleans become string `Config` values. Arrays,
inline tables containing non-scalars, dates, and times fail with `MADS020`
instead of being serialized ambiguously. File I/O and TOML parse errors also
use `MADS020` and name the path. I/O causes are retained, but raw TOML parse
errors are not exposed as sources because they can contain the offending
source line and therefore a secret value.

`DotenvSource` is an interpolation-variable source rather than a flattened
configuration source:

```rust
pub struct DotenvSource { /* path, required flag */ }

impl DotenvSource {
    pub fn optional(path: impl Into<std::path::PathBuf>) -> Self;
    pub fn required(path: impl Into<std::path::PathBuf>) -> Self;
}
```

`ConfigBuilder::dotenv(source)` registers it separately from normal
`ConfigSource`s. Missing optional files are accepted. Missing required files,
unreadable files, and malformed present files fail with `MADS020`, name the
path, and never include file contents or a parsed value. Raw dotenv parse errors
are not exposed as sources because they can contain the offending secret line.

Build order is exact:

1. load registered dotenv files in insertion order, with later files winning;
2. overlay Unicode variables from the real process environment;
3. load and merge normal `ConfigSource`s in their existing insertion order;
4. replace any complete config value matching `${NAME}` with the variable-map
   value; and
5. fail with `MADS020` when an exact placeholder is unresolved, using the
   configuration key as subject and naming only the missing variable.

The original configuration source remains attributed after interpolation.
Embedded forms such as `prefix-${NAME}`, default expressions, and recursive
interpolation remain literal and out of scope. A normal application uses:

```rust
let config = ConfigBuilder::new()
    .dotenv(DotenvSource::optional(".env"))
    .source(TomlSource::file("mads.toml"))
    .source(EnvSource::new("MADS_"))
    .build()?;
```

For placeholders, the real process environment overrides `.env`. Independently,
normal source precedence still means the final `EnvSource("MADS_")` can replace
a TOML key directly; for example, `MADS_DATABASE__URL` overrides
`database.url`. Neither behavior needs database-specific logic.

The resulting `Config` contains resolved values because consumers need them,
but `Config`, `ConfigValue`, `MapSource`, and `EnvSource` use custom `Debug`
implementations that redact stored values. Callers can still retrieve values
explicitly with `Config::get`; MADS cannot prevent an application from logging
a secret it explicitly requests.

### Typed database configuration

`DatabaseConfig` is the PostgreSQL pool configuration:

```rust
pub struct DatabaseConfig { /* redacted URL, pool size, startup flag */ }

impl DatabaseConfig {
    pub fn new(url: impl Into<String>) -> DatabaseResult<Self>;
    pub fn from_config(config: &mads_core::Config) -> DatabaseResult<Self>;
    pub fn with_pool_size(self, pool_size: usize) -> DatabaseResult<Self>;
    pub fn with_migrate_on_startup(self, enabled: bool) -> Self;
    pub const fn pool_size(&self) -> usize;
    pub const fn migrate_on_startup(&self) -> bool;
    pub fn url(&self) -> &str;
}
```

`DatabaseConfig::from_config` reads the already resolved core configuration and
applies these exact rules:

- `database.url` is required and must not be empty;
- a value that still has exact placeholder syntax is rejected defensively;
- `database.pool_size` defaults to `10`, must parse as `usize`, and must be at
  least `1`;
- `database.migrate` defaults to `false` and accepts only `true` or `false`;
- unknown `[database]` keys are ignored in v0.4 so future options do not break
  old binaries; and
- `Debug`, `Display`, and every diagnostic redact the URL.

Database configuration never reads the process environment itself. Exact
whole-value interpolation is a reusable `mads-core` build step.

## Database pool and execution API

`Database` is a cloneable application-scoped handle around one
`deadpool_diesel::postgres::Pool`:

```rust
#[derive(Clone)]
pub struct Database { /* shared pool */ }

impl Database {
    pub fn from_config(config: &DatabaseConfig) -> DatabaseResult<Self>;

    pub async fn run<T, F>(&self, operation: F) -> DatabaseResult<T>
    where
        T: Send + 'static,
        F: FnOnce(&mut diesel::PgConnection) -> diesel::QueryResult<T>
            + Send
            + 'static;

    pub async fn check(&self) -> DatabaseResult<()>;
    pub fn status(&self) -> DatabasePoolStatus;
    pub fn close(&self);
    pub fn is_closed(&self) -> bool;
}
```

`Database::from_config` creates exactly one pool with the configured maximum
size and Tokio runtime selection. It does not open a socket; deadpool creates
connections lazily. `check` acquires one connection and executes `SELECT 1`
through `run`, making readiness explicit.

`run` performs this sequence:

```text
acquire pooled PostgreSQL connection asynchronously
        |
        v
deadpool interact moves closure to a blocking worker
        |
        v
execute native Diesel closure with &mut PgConnection
        |
        v
normalize acquisition / interaction / query result
```

It never catches a panic and converts it into success. A blocking-worker panic
or cancellation becomes the interaction error variant. Values and closures
must be `Send + 'static` because they cross the blocking boundary.

`DatabasePoolStatus` is a MADS-owned snapshot with `max_size`, `size`,
`available`, and `closed` accessors. It avoids exposing deadpool as the normal
inspection API. `Database::close` is idempotent, rejects new acquisitions, and
drops idle connections; it does not promise to wait for checked-out
connections.

## Error normalization

Database operations return:

```rust
pub type DatabaseResult<T> = std::result::Result<T, DatabaseError>;

#[derive(Clone, Copy, Debug, Eq, PartialEq)]
pub enum DatabaseErrorKind {
    Configuration,
    Pool,
    Interaction,
    Query,
    Migration,
}

#[non_exhaustive]
pub enum DatabaseError {
    Configuration {
        message: String,
        source: Option<Box<dyn std::error::Error + Send + Sync>>,
    },
    Pool(deadpool_diesel::postgres::PoolError),
    Interaction(deadpool_diesel::InteractError),
    Query(diesel::result::Error),
    Migration(Box<dyn std::error::Error + Send + Sync>),
}
```

`DatabaseError` implements a custom redacted `Debug`, `Display`,
`std::error::Error`, and `kind()`. Its
configuration variant stores a structural message plus an optional boxed
source (used for pool-builder failures); the other public variants preserve the
deadpool pool error, interaction error, Diesel error, or boxed migration error
as the source. Messages describe the failed operation but never print the
database URL.

This is a normalization foundation, not an application error policy. In v0.4:

- Diesel `NotFound` remains a query error unless the repository uses
  `OptionalExtension`;
- unique and foreign-key violations remain inspectable through the preserved
  `diesel::result::Error` source;
- no database error automatically becomes an HTTP status; and
- `DatabaseErrorKind` is non-domain classification only.

`mads_common::MADS100` is the database bootstrap/configuration diagnostic code.
When a database error crosses into a MADS lifecycle hook or builder extension,
it is wrapped in `mads_core::Error` with `MADS100` and retained as its source.
`MADS101` remains reserved for v0.5 database auto-configuration failures.

## Migration API

MADS re-exports `diesel_migrations` and builds a small reporting layer over its
`MigrationHarness`:

```rust
pub struct MigrationReport {
    pub fn versions(&self) -> &[String];
    pub fn is_empty(&self) -> bool;
}

pub struct MigrationStatus {
    pub fn applied(&self) -> &[String];
    pub fn pending(&self) -> &[String];
}

impl Database {
    pub async fn run_pending_migrations<S>(
        &self,
        source: S,
    ) -> DatabaseResult<MigrationReport>
    where
        S: diesel::migration::MigrationSource<diesel::pg::Pg>
            + Send
            + 'static;

    pub async fn revert_last_migration<S>(
        &self,
        source: S,
    ) -> DatabaseResult<MigrationReport>
    where
        S: diesel::migration::MigrationSource<diesel::pg::Pg>
            + Send
            + 'static;

    pub async fn migration_status<S>(
        &self,
        source: S,
    ) -> DatabaseResult<MigrationStatus>
    where
        S: diesel::migration::MigrationSource<diesel::pg::Pg>
            + Send
            + 'static;
}
```

Each method acquires one connection and runs the complete harness operation on
one blocking worker. Versions are converted to owned strings before returning
across the async boundary. Applied and pending version lists are sorted in
ascending lexical order for deterministic CLI output. Status filters the
database's applied-version table to versions present in the supplied source,
so unrelated migration sources sharing a database are not reported. Rollback
likewise selects the greatest applied version present in the supplied source,
then calls `MigrationHarness::revert_migration`; unrelated applied sources do
not block it. If the source has no applied migration, it returns Diesel's
`MigrationError::NoMigrationRun` through `DatabaseError::Migration`. Diesel's
per-migration transaction policy remains authoritative.

Applications embed migrations with the re-exported macro:

```rust
use mads::diesel_migrations::{EmbeddedMigrations, embed_migrations};

const MIGRATIONS: EmbeddedMigrations = embed_migrations!("migrations");
```

File-based sources are used by the CLI. MADS does not introduce its own
migration file format.

## Explicit application bootstrap and lifecycle

Automatic provisioning belongs to v0.5. Version 0.4 uses an explicit builder
extension:

```rust
pub struct DatabaseBootstrap {
    config: DatabaseConfig,
    migrations: Option<diesel_migrations::EmbeddedMigrations>,
}

impl DatabaseBootstrap {
    pub fn new(config: DatabaseConfig) -> Self;
    pub fn with_migrations(
        self,
        migrations: diesel_migrations::EmbeddedMigrations,
    ) -> Self;
}

pub trait MadsBuilderDatabaseExt {
    fn database(
        &mut self,
        bootstrap: DatabaseBootstrap,
    ) -> mads_core::Result<&mut Self>;
}
```

The normal v0.4 bootstrap is:

```rust
let config = ConfigBuilder::new()
    .dotenv(DotenvSource::optional(".env"))
    .source(TomlSource::file("mads.toml"))
    .source(EnvSource::new("MADS_"))
    .build()?;
let database = DatabaseConfig::from_config(&config)?;
let mut builder = Mads::builder_with_config(config);
builder.database(DatabaseBootstrap::new(database).with_migrations(MIGRATIONS))?;
let application = builder.build().await?;
serve(application, "127.0.0.1:3000").await?;
```

`MadsBuilderDatabaseExt::database`:

1. validates startup migration consistency;
2. builds one `Database` pool;
3. calls the existing `MadsBuilder::provide(Database)` so the graph marks it
   `Provided` and repository constructors can resolve it; and
4. registers one database lifecycle hook.

If `database.migrate = true`, an embedded migration source is mandatory. The
extension returns `MADS100` before application construction when it is absent.
If `migrate = false`, an attached source remains available for manual calls but
is not run at startup.

The lifecycle hook does the following:

```text
application start
  -> Database::check
  -> if configured, run pending embedded migrations
  -> on readiness/migration failure, close this hook's pool before returning
  -> allow later lifecycle hooks and HTTP listener binding

application shutdown / startup rollback
  -> Database::close
```

Because v0.3 `serve` builds and validates the router before starting lifecycle,
invalid routes still fail before any database connection. Once lifecycle
starts, database readiness and migrations complete before listener binding.
Failure is reported as outer `MADS011` lifecycle context with an inner
`MADS100` database diagnostic and preserved `DatabaseError` cause. Because the
generic lifecycle manager rolls back only hooks that completed startup, the
database hook closes its own pool before returning a readiness or migration
failure.

Calling the extension twice or combining it with an already provided
`Database` produces the existing duplicate-provider failure. v0.4 does not
silently back off; that behavior belongs to v0.5.

## Repository experience and escape hatches

The managed-provider macro already clones dependency handles during graph
construction. Because `Database` is cloneable, the target repository works
without macro changes:

```rust
#[repository]
pub struct UserRepository {
    db: Database,
}

impl UserRepository {
    pub async fn find(&self, id: i64) -> DatabaseResult<Option<User>> {
        self.db
            .run(move |connection| {
                users::table
                    .find(id)
                    .select(User::as_select())
                    .first(connection)
                    .optional()
            })
            .await
    }
}
```

The facade exposes:

- `mads::diesel` for native query DSL, derives, PostgreSQL types, connection
  traits, and error inspection;
- `mads::diesel_migrations` for embedded/file sources and migration traits;
- `mads::common::database` as the owned integration module; and
- `Database`, `DatabaseBootstrap`, `DatabaseConfig`, `DatabaseError`,
  `DatabaseErrorKind`, `DatabasePoolStatus`, `DatabaseResult`,
  `MadsBuilderDatabaseExt`, `MigrationReport`, and `MigrationStatus` through
  the default prelude.

The core-only facade (`mads` with default features disabled) exposes none of
these types and has no database dependencies.

## CLI contract

The existing dependency-free parser style is retained; adding a command parser
framework is unnecessary for three fixed subcommands.

The supported syntax is exactly:

```text
mads db migrate
mads db rollback
mads db status
```

All three commands:

1. use the process current directory as the project root;
2. optionally load `<root>/.env` through `DotenvSource`, then require
   `<root>/mads.toml` through `TomlSource`, followed by `EnvSource("MADS_")`;
3. parse `DatabaseConfig` with the same rules as applications;
4. require a valid `<root>/migrations` directory through
   `FileBasedMigrations::from_path`;
5. create one `Database`, perform the requested operation, and close it; and
6. exit `1` with a redacted error on configuration, connection, or migration
   failure.

Output is deterministic:

```text
# migrate with work
applied 202608220001_create_users

# migrate without work
database is up to date

# rollback
reverted 202608220001_create_users

# status
applied 202608220001_create_users
pending 202608220002_add_user_name
summary: 1 applied, 1 pending
```

`rollback` reverts exactly one migration. If none are applied it exits `1` and
reports `no migration is available to revert`. `status` never changes schema.
Unknown database subcommands and extra arguments exit `2` and show help. The
general help lists the `db` command, and `mads db --help` lists all three
subcommands.

The library runner is refactored so parsing and async command execution can be
unit tested without calling `process::exit`; the binary is the only layer that
turns an exit status into `std::process::ExitCode`.

## Testing strategy

### Unit and offline tests

- `mads-core/tests/config.rs` covers TOML flattening, dotenv optional/required
  behavior, dotenv/process precedence, exact interpolation, source precedence,
  unsupported values, parse failures, lexical key order, and redacted
  diagnostics/`Debug` output.
- `mads-common/tests/database_config.rs` covers defaults, overrides, exact
  resolved values, unresolved-placeholder rejection, malformed booleans and
  sizes, zero pool size, and redacted `Debug`/errors.
- `mads-common/tests/database.rs` covers pool construction/status, clone-shared
  status, close idempotence, acquisition after close, error kinds, and source
  chaining without requiring a running server.
- `mads-common/tests/database_builder.rs` proves the builder provides exactly
  one `Database`, a `#[repository]` receives the same pool handle, missing
  startup migrations fail before build, and duplicate registration retains
  existing semantics.
- migration report/status ordering is unit-tested using focused internal
  helpers; real harness behavior is covered by PostgreSQL tests.
- `mads-cli` parser and process tests cover help, exit codes, unknown
  subcommands, missing files, optional project `.env`, process-environment
  override, malformed dotenv input, and redaction.
- facade tests prove all prelude and escape-hatch exports and preserve renamed
  and core-only consumer builds.

### PostgreSQL integration tests

CI adds a PostgreSQL 16 service with a health check and exports a dedicated
`MADS_TEST_DATABASE_URL`. Database tests are marked ignored for ordinary local
`cargo test` runs and run explicitly in the PostgreSQL CI job:

```text
cargo test -p mads-common --test database_postgres -- --ignored --test-threads=1
cargo test -p mads --test postgres_crud -- --ignored --test-threads=1
cargo test -p mads-cli --test database_cli -- --ignored --test-threads=1
```

The integration suite proves:

- pool readiness and close behavior against PostgreSQL;
- pending migrations apply once and status changes deterministically;
- rollback reverts exactly the latest migration;
- startup migration failure prevents later lifecycle hooks and listener bind;
- the generated provider graph injects `Database` into `UserRepository`;
- create, list, get, update, and delete use native Diesel DSL through
  `Database::run`; and
- the CRUD routes execute in-process through the existing Axum router.

Each database test serializes schema mutation, cleans table contents, and does
not assume test execution order. No test prints the database URL.

- require `.env` and `.env.*` in `.gitignore`, retain `.env.example`, and use
  only dummy values in tracked examples;
- show one native Diesel repository using `Database::run`;
- document embedded startup migrations and all three CLI commands;
- explain the blocking-worker boundary and pool lifecycle;
- preserve the Axum/Tower and Diesel escape hatches;
- add `docs/importance/version_0.4/diesel-persistence.md` and link it from

  labeled as future behavior.

## Edge cases and required behavior

1. Missing, empty, or unresolved `database.url` fails before pool creation.
2. Pool size `0`, negative text, non-numeric text, and overflow fail with a
   configuration error.
3. `database.migrate` values other than literal `true` or `false` fail.
4. Missing optional `.env` succeeds; missing required, unreadable, or malformed
   dotenv input fails with a redacted `MADS020`.
5. Exact `${NAME}` interpolation fails when `NAME` is absent or non-Unicode;
   embedded placeholders remain literal.
6. Real process variables override dotenv variables; later dotenv sources
   override earlier dotenv sources without mutating the process environment.
7. URLs and resolved secrets never appear in MADS-owned `Debug`, errors, CLI
   stderr, or test failure messages authored by MADS.
8. A closed pool rejects new `run`, readiness, and migration operations with
   `DatabaseErrorKind::Pool`.
9. Query errors retain the original `diesel::result::Error` source.
10. A panic/cancellation in a blocking interaction is not misclassified as a
   Diesel query failure.
11. Running pending migrations twice applies each migration once.
12. Startup migration mode without embedded migrations fails during explicit
    builder registration, before application construction.
13. Database readiness or migration failure stops lifecycle startup; later
    hooks and HTTP binding do not run.
14. Shutdown and startup rollback close the pool; repeated close is harmless.
15. Manual migration APIs work regardless of `database.migrate`; that flag
    controls startup only.
16. `rollback` reverts one migration from its supplied source, ignores
    unrelated applied sources, and fails clearly when that source has no
    applied migration.
17. `status` reports deterministic applied and pending lists and makes no
    changes.
18. Supplying `Database` satisfies the existing graph node and prevents any
    generated constructor attempt; no core graph changes are required.
19. Existing HTTP route validation still occurs before lifecycle and therefore
    before a database connection is attempted by `serve`.
20. Documented projects ignore `.env` and `.env.*`, retain `.env.example`, and
    commit only placeholders/dummy values.
21. Core-only builds and renamed dependencies retain their v0.3 behavior.

## Acceptance criteria

The milestone is accepted only when all of the following are true:

1. The workspace version is 0.4.0 and the MSRV remains Rust 1.85.0.
2. `mads-core` has no database-specific normal dependency or semantic branch.
3. TOML values and optional dotenv variables load through the generic core
   pipeline with exact interpolation, process-environment precedence, no
   process mutation, and redacted diagnostics/`Debug` output.
4. `DatabaseConfig` implements the documented defaults, resolved-value
   validation, and redaction rules.
5. One `Database` owns one PostgreSQL pool and clones share that pool.
6. `Database::run` executes native Diesel closures off Tokio workers and
   returns normalized, source-preserving errors.
7. Embedded and file-based migration sources support apply, single rollback,
   and status reporting.
8. Explicit builder registration makes `Database` a provided graph node and
   registers readiness/migration/close lifecycle behavior.
9. Startup migration failure occurs before listener binding and later hooks.
10. `mads db migrate`, `rollback`, and `status` match the CLI contract and
    never expose credentials.
11. A real PostgreSQL integration test completes create/list/get/update/delete
    through a `#[repository]` that receives `Database` from the graph.
12. Direct Diesel DSL, Diesel errors, migration APIs, Axum, and Tower remain
    accessible as documented escape hatches.
13. Existing v0.3 HTTP tests, core-only tests, renamed-consumer tests, MSRV,
    rustdoc, clippy, formatting, and 85% coverage all pass.
14. Documentation presents v0.4 behavior as available and leaves v0.5+
    behavior explicitly deferred.

## Resolved decisions

- PostgreSQL is the sole v0.4 backend.
- `deadpool-diesel` is the pooling/blocking adapter.
- Diesel and migrations are pinned to their Rust-1.85-compatible 2.2 releases.
- Generic optional `.env` loading belongs to `mads-core`; it is not a database
  special case.
- `.env` never mutates process state, and real process variables override it.
- Project `.env` files are ignored by Git while `.env.example` remains tracked.
- Database registration is explicit; auto-configuration waits for v0.5.
- Startup migrations use embedded migrations; CLI commands use file-based
  migrations.
- Database error normalization does not imply HTTP/domain mapping.
- The existing repository macro requires no v0.4 syntax change.
- CLI commands use the current project directory and fixed default file paths.
- PostgreSQL integration is mandatory in CI and opt-in for ordinary local test
  runs.

There are no unresolved implementation decisions in this specification.
