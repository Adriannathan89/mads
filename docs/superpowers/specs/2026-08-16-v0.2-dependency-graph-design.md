# MADS.rs v0.2 Dependency and Application Graph Design

## Purpose

This specification defines MADS.rs v0.2.0, Dependency and Application Graph.
It evolves the explicit v0.1 provider foundation into a deterministic,
type-driven graph that is fully validated before provider construction or
application startup.

The graph is assembled at startup from metadata generated at compile time.
Graph planning never occurs during request handling. This milestone remains
framework-neutral and does not introduce HTTP, persistence, or module graph
semantics.

## Goals

Version 0.2 must provide:

- provider nodes and dependency edges keyed by concrete Rust types;
- a side-effect-free graph analysis API;
- exact duplicate provider detection;
- ambiguous output binding detection;
- unresolved dependency detection;
- readable dependency cycle detection;
- deterministic topological construction planning;
- automatic application-scoped provider construction;
- provider visibility metadata as a foundation for future modules;
- immutable graph and construction-plan inspection after a successful build;
- aggregated, deterministic graph diagnostics;
- an explicit-value override path and a manual-construction escape hatch.

## Non-Goals

Version 0.2 does not include:

- Axum, HTTP routes, extractors, responses, or server startup;
- Diesel, database pools, migrations, or database auto-configuration;
- module imports, exports, ownership, visibility enforcement, or route paths;
- trait bindings, qualifiers, named providers, or
  `#[repository(as = Trait)]`;
- request or transient provider scopes;
- concurrent provider construction;
- constructor rollback or resource-cleanup protocols;
- graph text or JSON rendering in the CLI;
- Redis, caching, rate limiting, background jobs, or other optional policies.

## Architectural Model

Version 0.2 uses a hybrid compile-time and startup-runtime model:

```text
compile-time macro descriptors
          +
explicitly provided values
          |
          v
side-effect-free graph analysis
          |
          v
deterministic validation report
          |
          v
topological construction plan
          |
          v
sequential provider construction
          |
          v
immutable Mads application
```

Procedural macros continue to generate static provider and dependency
metadata. During `MadsBuilder::build().await`, MADS collects that metadata,
builds the graph, validates the complete graph, computes a construction plan,
and constructs application-scoped providers. The completed application uses
the existing registry; it does not perform graph planning during normal
runtime resolution.

The graph subsystem belongs in `mads-core` and is divided into focused units:

```text
graph       immutable nodes, edges, origins, states, and inspection APIs
analysis    normalization, conflict checks, edge resolution, and cycles
plan        deterministic topological construction order
builder     analysis and construction orchestration
```

Existing registry, catalog, descriptor, macro, lifecycle, and diagnostic
components receive only the focused extensions required by these units.

## Graph Scope

Until module relationships are introduced in v0.6, the complete deterministic
provider catalog is the v0.2 application graph. Every discovered provider is
included and constructed even when no other provider depends on it.

The v0.2 `ApplicationGraph` models providers and their dependencies only.
Existing module descriptors remain available through `Catalog`, but they do
not become isolated graph nodes and do not imply ownership, imports, exports,
or reachability.

The graph is keyed internally by concrete `TypeId`. Public inspection uses
stable Rust type names and source locations. Trait objects, named bindings,
qualifiers, and other binding-selection semantics are deferred.

## Public Graph Model

The public graph API consists of these immutable types:

```rust
pub struct ApplicationGraph { /* ordered provider nodes and dependency edges */ }
pub struct ProviderNode { /* type, origin, visibility, source, and state */ }
pub struct DependencyEdge { /* provider to required type */ }
pub struct ConstructionStep { /* one statically declared provider */ }
pub struct ConstructionPlan { /* deterministic ordered construction steps */ }
pub struct GraphAnalysis { /* graph, diagnostics, and optional plan */ }

pub enum ProviderOrigin {
    Provided,
    Service,
    Repository,
    Provider,
}

pub enum ProviderVisibility {
    Public,
    Private,
}

pub enum ProviderState {
    Provided,
    Preconstructed,
    Planned,
}
```

Fields remain private. The read-only inspection contract is:

```rust
impl ApplicationGraph {
    pub fn providers(&self) -> &[ProviderNode];
    pub fn dependencies(&self) -> &[DependencyEdge];
    pub fn provider<T>(&self) -> Option<&ProviderNode>
    where
        T: Send + Sync + 'static;
}

impl ProviderNode {
    pub fn type_name(&self) -> &str;
    pub const fn origin(&self) -> ProviderOrigin;
    pub const fn visibility(&self) -> ProviderVisibility;
    pub const fn state(&self) -> ProviderState;
    pub const fn location(&self) -> Option<SourceLocation>;
    pub fn declared_dependencies(&self) -> &[DependencyDescriptor];
}

impl DependencyEdge {
    pub fn provider_type_name(&self) -> &str;
    pub fn dependency_type_name(&self) -> &str;
}

impl ConstructionStep {
    pub fn type_name(&self) -> &str;
    pub const fn origin(&self) -> ProviderOrigin;
    pub const fn location(&self) -> SourceLocation;
}

impl ConstructionPlan {
    pub fn steps(&self) -> &[ConstructionStep];
}

impl GraphAnalysis {
    pub const fn graph(&self) -> &ApplicationGraph;
    pub fn diagnostics(&self) -> &[Diagnostic];
    pub const fn construction_plan(&self) -> Option<&ConstructionPlan>;
    pub fn is_valid(&self) -> bool;
}
```

These accessors expose:

- stable output type name and internal type identity;
- provider origin;
- provider state for the current builder;
- public or private visibility metadata;
- source location for statically declared providers;
- declared dependency types in source declaration order;
- resolved dependency edges;
- deterministic construction order when the graph is valid.

Collections returned for inspection are immutable and deterministically
ordered. `pub` declarations are recorded as public. Inherited and restricted
visibilities, including `pub(crate)`, are recorded as private for the v0.2
two-state foundation. Values inserted through `MadsBuilder::provide` have no
Rust declaration visibility and are recorded as public because they are
application-wide in v0.2. Visibility is descriptive only; enforcement
requires the module semantics scheduled for v0.6.

## Builder API and Compatibility

Automatic graph construction becomes the default. The primary API is:

```rust
let mut builder = Mads::builder();
builder.provide(external_value)?;
let mut app = builder.build().await?;
```

`MadsBuilder::build` becomes asynchronous and fallible:

```rust
pub async fn build(self) -> Result<Mads>;
```

This is an intentional pre-1.0 breaking change from the synchronous,
infallible v0.1 method.

The builder also exposes side-effect-free analysis:

```rust
pub fn analyze(&self) -> GraphAnalysis;
```

`analyze()` invokes no provider constructor. It returns the discovered graph,
all safely detectable diagnostics, and a construction plan only when the graph
is valid. `build().await` runs the same analysis before performing any
construction.

The completed application exposes its validated artifacts:

```rust
pub const fn graph(&self) -> &ApplicationGraph;
pub const fn construction_plan(&self) -> &ConstructionPlan;
```

Access remains read-only and allocation-free.

`MadsBuilder::construct::<T>().await` remains supported as an advanced escape
hatch. A manually constructed static provider is marked `Preconstructed` and
is not constructed again by `build()`.

## Explicit Values and Provider Selection

`MadsBuilder::provide<T>(value)` supplies an application-scoped value and
creates a satisfied `Provided` graph node. The configuration value inserted by
`MadsBuilder::new` follows the same model and appears in inspection results.

An explicit value wins over the single discovered provider for the same output
type. The descriptor remains relevant for conflict validation, but its
constructor is suppressed and its dependencies are not active because the
effective node is the provided value.

Explicit provision does not hide catalog defects. If multiple different
descriptors produce the same type, the graph remains ambiguous and invalid
even when a value for that type was explicitly supplied.

Provider conflicts have distinct meanings:

- an exact duplicate is the same provider identity or descriptor registered
  more than once;
- an ambiguous binding consists of different provider declarations producing
  the same concrete output type.

## Analysis Pipeline

Graph analysis runs these stages in order:

1. Collect registry metadata for provided and preconstructed values.
2. Collect all provider descriptors from `Catalog`.
3. Sort descriptors by stable output type name, provider kind, and source
   location.
4. Detect exact duplicate descriptors.
5. Detect different descriptors that produce the same output type.
6. Select one effective node per unambiguous type, honoring explicit values.
7. Resolve declared dependency types to effective provider nodes.
8. Report unresolved dependencies.
9. Detect cycles across unambiguous, fully resolved static nodes.
10. Produce a stable topological construction plan if no blocking diagnostic
    remains.

Ambiguous dependencies do not also produce missing-dependency diagnostics.
Cycle detection excludes unresolved or ambiguous edges so validation does not
produce misleading cascades.

## Deterministic Ordering

Inventory registration order and hash-map iteration order must never affect
the graph, diagnostics, or construction plan.

Provider ordering uses stable output type name, provider kind, and source
location. Dependency order preserves source declaration order for inspection.
When multiple nodes are simultaneously eligible during topological sorting,
the same stable provider ordering selects the next node.

Provided and preconstructed nodes participate in graph inspection and edge
resolution but do not appear as executable construction steps. All remaining
static nodes appear exactly once in the plan.

Provider construction is sequential in v0.2. This preserves deterministic
side effects, failure selection, and diagnostics. Construction by independent
dependency level may be added later without changing graph semantics.

## Cycle Detection

Cycle diagnostics must display a deterministic, readable closed path, for
example:

```text
ServiceA -> RepositoryB -> ServiceC -> ServiceA
```

Self-cycles are valid cycle failures and render the provider twice to show the
closed edge. When more than one traversal could represent the same cycle, MADS
canonicalizes the path using stable provider ordering so output does not
depend on discovery order.

## Construction Execution

After successful analysis, `build().await`:

1. starts with `Config`, explicitly provided values, and manually
   preconstructed providers already in the registry;
2. executes each planned constructor sequentially;
3. inserts each constructed value before executing dependent constructors;
4. aborts immediately if a constructor fails;
5. returns `Mads` only after every planned constructor succeeds;
6. stores the validated graph and the exact executed plan in `Mads`.

Graph validation always completes before the first automatic constructor is
invoked. Invalid graphs therefore have no provider-construction side effects.

If a constructor fails, the partially built builder is consumed and no
application is returned. Version 0.2 does not add constructor rollback.
Resources requiring controlled startup and shutdown must use the existing
lifecycle-hook model. Lifecycle hooks are not started during graph
construction.

## Diagnostics and Reports

Version 0.2 assigns these meanings:

```text
MADS001  exact duplicate provider descriptor
MADS002  ambiguous provider binding
MADS003  unresolved dependency
MADS005  dependency cycle
MADS006  provider construction failure
```

Existing registry mismatch, lifecycle, hook, and configuration diagnostic
codes retain their current meanings.

Graph validation aggregates all independent diagnostics that can be reported
safely. Diagnostics are ordered by category, subject type, and source
location. Checks that depend on resolving an earlier ambiguity or missing edge
are suppressed rather than emitting speculative follow-on errors.

The error model is extended to carry a deterministic diagnostic report while
preserving the existing single-diagnostic API:

- `Error::code()` returns the primary diagnostic code;
- existing single-diagnostic constructors remain supported;
- `Error::diagnostics()` exposes all diagnostics in report order;
- display output renders all diagnostics in the same stable order;
- underlying error sources remain available through Rust's error chain.

`GraphAnalysis` exposes diagnostics directly so invalid graphs can be
inspected without attempting construction.

A provider construction failure identifies the failing provider, its source
location, and a canonical dependency or consumer path when one is available.
The underlying constructor error is preserved as the source.

## Macro and Descriptor Changes

Service, repository, and provider descriptors gain visibility metadata.
Managed-struct macros and the provider-function macro derive it from the
declaration visibility. Existing dependency metadata and constructors remain
the graph input and must not require application code to repeat dependency
lists.

The descriptor meaning established in v0.1 remains valid: each dependency
entry represents one directed edge from the provider to its required concrete
type. The graph subsystem consumes that metadata rather than introducing a
second registration mechanism.

Provider registry entries gain enough stable metadata for `analyze()` to
represent provided and preconstructed values without cloning, resolving, or
executing them.

## Testing Strategy

Implementation follows red-green-refactor and preserves the existing testing
style.

Focused graph tests cover:

- deterministic node, edge, and topological ordering;
- dependency-free and disconnected providers;
- complete-catalog inclusion of otherwise unused providers;
- explicit-value override behavior;
- manual preconstruction behavior;
- exact duplicates and ambiguous output bindings;
- one and multiple unresolved dependencies;
- self-cycles and multi-node canonical cycle paths;
- aggregated diagnostics and cascade suppression;
- invalid graphs invoking zero constructors;
- dependency-ordered sequential construction;
- constructor failure source preservation;
- side-effect-free repeated analysis;
- immutable graph and plan inspection.

Macro and integration tests cover:

- private, restricted, and public visibility metadata;
- service, repository, and provider dependency edges;
- automatic transitive construction without manual ordering;
- provided configuration and external dependency nodes;
- inspection through a successfully built `Mads`;
- continued use of explicit manual construction.

Test helpers should permit analysis of isolated descriptor sets without
polluting unrelated tests through process-wide inventory. Public production
behavior still uses the complete catalog.

## Documentation and Release Changes

Completing this milestone updates the workspace version, facade, CLI version
output, and current documentation from `0.1.0` to `0.2.0`.

The README must document:

- automatic asynchronous and fallible `build()`;
- the explicit-value and manual-construction escape hatches;
- graph analysis and inspection;
- deterministic validation and construction behavior;
- graph diagnostic codes;
- visibility metadata without enforcement;
- all deferred capabilities.

The CLI does not gain the final `mads graph` renderer in this milestone. Its
version output changes to 0.2.0, while the internal graph model needed by a
future command becomes available through `mads-core`.

## Verification Gates

Version 0.2 retains:

- Rust 2024 and Rust 1.85 MSRV;
- compiler-enforced crate dependency direction;
- formatting and Clippy with warnings denied;
- complete workspace tests and doctests;
- rustdoc with warnings denied;
- architecture dependency checks;
- at least 85 percent workspace LLVM line coverage;
- meaningful module and public-item documentation;
- `#![forbid(unsafe_code)]` throughout publishable crates.

## Acceptance Criteria

Version 0.2 is complete when:

1. Every discovered provider and every supplied value appears in a stable
   application graph.
2. Exact duplicates, ambiguity, missing dependencies, and cycles are detected
   before any automatic constructor runs.
3. Independent validation errors are aggregated without misleading cascades.
4. Valid graphs produce the same construction plan regardless of registration
   order.
5. Automatic construction follows dependency order and constructs every
   planned provider exactly once.
6. Explicit values satisfy and override a single matching descriptor.
7. Manual construction remains available and is not repeated automatically.
8. Cycle diagnostics contain a deterministic readable path.
9. Graph analysis is side-effect-free and invalid graphs remain inspectable.
10. Successful applications retain immutable graph and plan inspection data.
11. Provider visibility is recorded but not enforced without modules.
12. The workspace reports version 0.2.0 and passes every stable, MSRV,
    documentation, architecture, and coverage gate.
13. HTTP, Diesel, module semantics, trait bindings, qualifiers, additional
    scopes, and future CLI rendering have not leaked into the milestone.

## Evolution Beyond v0.2

The v0.3 HTTP adapter can consume the validated provider graph without
changing its construction semantics. The v0.5 auto-configuration engine can
extend provider selection with capability-driven defaults and back-off. The
v0.6 module graph can add ownership, imports, exports, visibility enforcement,
and reachable roots around the provider graph established here.

Those milestones may extend graph metadata and selection inputs, but they must
not invalidate the v0.2 guarantees of deterministic analysis, validation
before construction, inspectability, and stable dependency ordering.
