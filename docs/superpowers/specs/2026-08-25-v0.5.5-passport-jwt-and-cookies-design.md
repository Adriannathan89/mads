# MADS.rs v0.5.5 Passport, JWT, Guards, and Cookies Design

## Status

The decisions in this specification are approved in chat. This written form is
the review checkpoint and, once approved, becomes the design input for the
v0.5.5 implementation plan. It replaces the authentication and cookie portion
of the existing v0.5.5 roadmap. The CORS and HTTP auto-binding work previously
grouped with v0.5.5 moves to v0.5.6.

> **Roadmap supersession (v0.6.0):** The planned v0.5.6 CORS and HTTP
> auto-binding milestone was merged into v0.6.0 so it could share the root
> module scope with provider, route, guard, and strategy discovery.

## Objective

Version 0.5.5 adds first-class cookie handling and a Passport-inspired JWT
authentication model without introducing HTTP or cryptography dependencies into
`mads-core`.

The target developer experience is:

```toml
[passport]
secret = "${JWT_SECRET}"
```

```rust
#[routes(prefix = "/users")]
#[guard(
    strategy = "jwt",
    principal = UserPrincipal,
    source = bearer,
    roles(any = ["user"]),
)]
trait UserRoutes {
    #[get("/profile")]
    #[guard(permissions(all = ["profile:read"]))]
    async fn profile(
        &self,
        authenticated: Authenticated<UserPrincipal>,
    ) -> HttpResult<Json<Profile>>;
}
```

The framework owns token extraction, cryptographic verification, standard-claim
validation, named-strategy resolution, route policy evaluation, and HTTP failure
mapping. Application strategies own application-specific identity validation.

## Release boundary

### v0.5.5 includes

- scalar and string-array configuration;
- complete request-cookie parsing and `Set-Cookie` response support;
- application-scoped `JwtService` auto-configuration;
- HS256, HS384, HS512, RS256, RS384, RS512, ES256, and ES384;
- inline and file-backed key material;
- signing-key rotation through a named key ring;
- registered-claim validation and typed custom claims;
- distinct access and refresh JWT profiles;
- named, managed Passport strategies;
- typed authenticated principals;
- route-trait and route-method `#[guard]` policies;
- Bearer and cookie token sources;
- roles, permissions, and synchronous principal predicates;
- native Axum cookie and authentication composition;
- redacted diagnostics and auto-configuration inspection.

### v0.5.5 does not include

- login, credential validation, or password hashing;
- a built-in refresh endpoint;
- refresh-token persistence, rotation, reuse detection, or revocation;
- a Redis or PostgreSQL refresh-token store;
- CSRF middleware;
- CORS;
- HTTP host/port auto-binding;
- remote JWKS fetching or discovery;
- JWE encryption;
- module reachability or export enforcement;
- non-JWT Passport strategies.

Applications use `JwtService` to issue refresh JWTs and implement refresh-token
storage and rotation in their own strategy/service logic. v0.5.6 owns CORS and
HTTP auto-binding. v0.6.0 applies root-module reachability and visibility rules
to the strategy metadata introduced here.

> **Roadmap supersession (v0.6.0):** The planned v0.5.6 CORS and HTTP
> auto-binding milestone was merged into v0.6.0 so it could share the root
> module scope with provider, route, guard, and strategy discovery.

## Reference model

The division follows the NestJS Passport/JWT model while using Rust-native,
type-driven APIs:

- `JwtService` is the stable signing and verification utility;
- a Passport strategy validates verified claims into an application principal;
- a guard selects a named strategy and controls whether a route executes;
- refresh behavior belongs to application authentication logic.

The design also follows the JWT Best Current Practices requirements to pin
allowed algorithms, bind keys to one algorithm, explicitly type different JWT
kinds, and use mutually exclusive validation rules.

Primary references:

- [NestJS Passport JWT](https://docs.nestjs.com/recipes/passport#implementing-passport-jwt)
- [NestJS JWT service](https://github.com/nestjs/jwt)
- [RFC 8725: JWT Best Current Practices](https://www.rfc-editor.org/rfc/rfc8725.html)
- [RFC 9700: OAuth 2.0 Security Best Current Practice](https://www.rfc-editor.org/rfc/rfc9700.html)
- [RFC 9068: OAuth JWT Access Token Profile](https://www.rfc-editor.org/rfc/rfc9068.html)

MADS does not claim RFC 9068 compliance because its generic JWT profile does not
require every RFC 9068 claim. It therefore uses private explicit token types
rather than the registered `at+jwt` type.

## Architecture

```text
mads-core
├── backward-compatible scalar configuration
├── generic string-array configuration
├── existing auto-configuration engine
└── provider/module graph contracts
         ↑
mads-common
├── cookie        Axum request and response cookie integration
├── jwt           keys, claims, signing, verification, auto-configuration
└── passport      strategies, principals, guard catalog and runtime
         ↑
mads-common-macros
├── #[guard]
├── #[passport_strategy]
└── #[derive(PassportPrincipal)]
         ↑
mads
└── feature-gated facade exports and prelude
```

`mads-core` remains free of Axum, HTTP, cookie, and cryptography dependencies.
`mads-extra` remains unchanged. The new behavior lives in focused
`mads-common` modules because it is a first-class HTTP capability rather than a
post-v1 extension.

The `common` compatibility feature does not automatically enable `jwt` or

The implementation pins:

```toml
jsonwebtoken = { version = "=10.3.0", default-features = false, features = ["rust_crypto", "use_pem"] }
```

meet the workspace contract. `axum-extra` remains at the workspace's 0.12.6
line and enables its `cookie` feature only when MADS cookie support is selected.

## Generic string-array configuration

The existing scalar API remains source-compatible:

```rust
Config::get(&self, key: &str) -> Option<&str>;
Config::source_of(&self, key: &str) -> Option<&str>;
ConfigSource::load(&self) -> Result<BTreeMap<String, String>>;
```

A new public configuration document and defaulted source method add arrays
without breaking existing `ConfigSource` implementations:

```rust
pub struct ConfigDocument { /* scalar and string-array entries */ }

pub trait ConfigSource: Send + Sync {
    fn name(&self) -> &str;
    fn load(&self) -> Result<BTreeMap<String, String>>;

    fn load_document(&self) -> Result<ConfigDocument> {
        self.load().map(ConfigDocument::from_scalars)
    }
}
```

`TomlSource` overrides `load_document` and accepts arrays containing only
strings. Integer, float, boolean, datetime, mixed, nested, and array-of-table
array values remain unsupported. Existing scalar TOML behavior remains
unchanged.

`Config` adds:

```rust
pub fn get_string_array(&self, key: &str) -> Option<&[String]>;
pub fn source_of_string_array(&self, key: &str) -> Option<&str>;
```

`ConfigDocument` and `MapSource` provide programmatic string-array insertion.
When a later source supplies the same key with a different value shape, the
later scalar or array replaces the earlier value completely. Every string-array
element supports the same exact `${NAME}` interpolation as scalar strings.
Dotenv variables remain interpolation inputs rather than configuration values,
and process variables continue to override dotenv variables.

`EnvSource` remains scalar-only in v0.5.5; it does not invent a delimiter or
JSON convention for arrays. Arrays come from TOML or explicit programmatic
documents.

Each merged scalar or array retains a structured origin containing its public
source label and an optional relative-path base. `TomlSource` sets that base to
the source file's parent directory. Default `ConfigSource` implementations,
`EnvSource`, and programmatic sources leave it absent, which means the process
working directory. Existing `source_of` methods continue to return only the
public label. A generic path-resolution helper uses the winning value's origin;
JWT code does not infer a filesystem directory from a display label.

Configuration loading remains explicit. `Mads::builder()` does not start
loading `.env`, `mads.toml`, or process variables in v0.5.5.

## Passport configuration

### Simple HMAC mode

The minimal configuration is:

```toml
[passport]
secret = "${JWT_SECRET}"
```

This means exactly one allowed algorithm, HS256. The secret is interpreted as
UTF-8 bytes and must contain at least 32 bytes. There is no algorithm inference
from a token header.

An application selecting another single HMAC algorithm declares it explicitly:

```toml
[passport]
secret = "${JWT_SECRET}"
algorithms = ["HS512"]
```

Top-level `secret` mode permits exactly one HS algorithm. It rejects asymmetric
algorithms, more than one allowed algorithm, `active_key`, or nested keys.
Minimum secret sizes are:

| Algorithm | Minimum bytes |
| --- | ---: |
| HS256 | 32 |
| HS384 | 48 |
| HS512 | 64 |

Weak secrets are startup errors, not warnings.

### Common validation policy

Optional common keys are:

```toml
[passport]
issuer = "https://auth.example.com"
audiences = ["mads-api"]
clock_skew_seconds = 30
max_token_bytes = 8192
```

Defaults and constraints are:

- `clock_skew_seconds` defaults to `0` and must be a non-negative integer;
- `max_token_bytes` defaults to `8192` and must be positive;
- `exp` is required and always validated;
- `nbf` is optional and validated when present;
- `iss` is required and must match exactly when `issuer` is configured;
- `aud` is required and must contain an expected value when `audiences` is
  configured;
- `sub` is optional unless call-specific validation requires it;
- configured issuer and audiences are inserted during signing;
- per-call validation may add restrictions but cannot disable configured ones.

When multiple configured audiences exist, verification succeeds when the
token contains at least one configured audience, and MADS-issued tokens contain
the complete configured audience list.

### Named key-ring mode

Key rotation uses deterministic named tables:

```toml
[passport]
active_key = "2026-08"
algorithms = ["RS256"]
issuer = "https://auth.example.com"
audiences = ["mads-api"]

[passport.keys."2026-08"]
algorithm = "RS256"
private_key_file = "keys/current-private.pem"
public_key_file = "keys/current-public.pem"

[passport.keys."2026-07"]
algorithm = "RS256"
public_key = "${PREVIOUS_PUBLIC_KEY_PEM}"
```

Key IDs are 1 through 128 ASCII characters and may contain letters, digits,
period, underscore, and hyphen. The table name is the JWT `kid`.

Each key declares exactly one algorithm, and that algorithm must occur in the
root `algorithms` allowlist. Named key-ring mode therefore requires a non-empty
root allowlist. A key can never be reused with another algorithm. The active key
signs and verifies. Previous keys verify only. Every key-ring JWT must contain
`kid`; a missing or unknown ID is rejected before signature verification.

HMAC key entries require `secret`. RSA and EC verification keys require exactly
one of `public_key` and `public_key_file`. The active RSA or EC signing key also
requires exactly one of `private_key` and `private_key_file`. Supplying both an
inline value and a file for the same material is invalid. Previous asymmetric
keys do not need private material.

Relative key paths supplied by `mads.toml` resolve from that TOML file's parent
directory. Relative paths supplied by environment or programmatic sources
resolve from the process working directory. Absolute paths remain absolute.

The evaluator reads and validates configured key files to make missing,
unreadable, or malformed keys analysis failures. This validation does not
retain cryptographic key objects or key bytes. After combined graph validation,
the applier constructs the selected cryptographic key objects once and caches
them in the application-scoped service. Neither phase retains key bytes in
reports.

## JWT data model

MADS owns registered and framework claims while applications own custom claims:

```rust
pub enum JwtTokenKind {
    Access,
    Refresh,
}

pub struct JwtClaims<C> {
    pub registered: RegisteredJwtClaims,
    pub custom: C,
}

pub struct VerifiedJwt<C> {
    pub header: JwtHeader,
    pub claims: JwtClaims<C>,
}
```

The serialized claims are flat JSON. MADS-owned names cannot be supplied by the
custom claim object. Custom claims must serialize to a JSON object. A scalar,
array, or null custom value is rejected. MADS separates reserved fields from
the remaining object before deserializing `C`, and signing or verification
rejects every reserved-name collision instead of accepting duplicate keys.

The MADS-owned claims are:

```text
iss        optional unless configured
sub        optional unless required per call
aud        optional unless configured
exp        required
nbf        optional
iat        required on MADS-issued tokens
jti        optional unless required per call
token_use  required: "access" or "refresh"
```

MADS-issued access and refresh tokens are mutually exclusive in two places:

| Kind | `typ` header | `token_use` claim |
| --- | --- | --- |
| Access | `mads-access+jwt` | `access` |
| Refresh | `mads-refresh+jwt` | `refresh` |

Both values must match the validation policy. A refresh token cannot authorize
an access-token route even when it uses the same signing key.

## JwtService API

`JwtService` is cloneable, application-scoped, and safe to inject into managed
providers. Its primary API is:

```rust
impl JwtService {
    pub fn sign<C>(
        &self,
        custom_claims: C,
        options: JwtSignOptions,
    ) -> JwtResult<String>
    where
        C: serde::Serialize;

    pub fn verify<C>(
        &self,
        token: &str,
        validation: JwtValidation,
    ) -> JwtResult<VerifiedJwt<C>>
    where
        C: serde::de::DeserializeOwned;

    pub fn decode_header(&self, token: &str) -> JwtResult<JwtHeader>;

    pub fn decode_unverified<C>(&self, token: &str) -> JwtResult<JwtClaims<C>>
    where
        C: serde::de::DeserializeOwned;
}
```

There is no ambiguous plain `decode` method. `decode_header` and
`decode_unverified` document that their output is untrusted.

Signing requires a positive lifetime and an explicit kind:

```rust
JwtSignOptions::access(Duration::from_secs(900))
    .subject(user_id.to_string())
    .jwt_id(token_id.to_string());

JwtSignOptions::refresh(Duration::from_secs(604_800))
    .subject(user_id.to_string())
    .jwt_id(refresh_id.to_string());
```

`iat` and `exp` are calculated by MADS. Options may add `nbf`, `sub`, and `jti`.
The service refuses zero lifetimes and timestamp overflow. It selects only the
active configured key for signing.

Verification rejects input larger than `max_token_bytes` before JSON or crypto
work. It reads the untrusted header only to select a configured `kid`, then
checks that the header algorithm exactly matches the selected key and allowlist
before verifying. `none`, an unconfigured algorithm, a mismatched algorithm
family, arbitrary `jku`/`x5u`, and unknown keys are always rejected.

`JwtValidation` has explicit `access()` and `refresh()` constructors and no
kind-neutral default. Direct service callers therefore choose the expected
token kind just as a Passport strategy does through `TOKEN_KIND`.

## Cookie API

The `cookies` feature exposes:

```rust
Cookie
CookieJar
Expiration
SameSite
cookie::time
```

`CookieJar` is a MADS newtype backed by `axum-extra`'s cookie integration. The
newtype supplies MADS validation and redacted debugging while retaining Axum's
request extractor and response-parts composition.

```rust
async fn login(jar: CookieJar) -> HttpResult<(CookieJar, Json<LoginResponse>)> {
    let cookie = Cookie::build(("refresh_token", token))
        .path("/")
        .http_only(true)
        .secure(true)
        .same_site(SameSite::Strict)
        .max_age(cookie::time::Duration::days(7))
        .build();

    Ok((jar.add(cookie), Json(response)))
}
```

The jar supports request parsing, `get`, `iter`, `add`, `remove`, and multiple
`Set-Cookie` response headers. `Cookie` exposes `Path`, `Domain`, `Max-Age`,
`Expires`, `HttpOnly`, `Secure`, and `SameSite`.

Outgoing cookie names and values must encode as valid headers. Invalid cookies
produce a typed response-parts rejection and no partial `Set-Cookie` output.
`SameSite=None` with explicitly disabled `Secure` is rejected. The jar's `Debug`
output reports counts and pending operations but not cookie names or values.

Ordinary malformed cookie requests produce `400 Bad Request`. For authentication
cookie extraction, a missing, malformed, or duplicated target cookie maps to
generic `401 Unauthorized`. A guard never chooses between duplicate cookies of
the same target name.

Cookie authentication does not implement CSRF protection. Documentation and
examples require explicit application CSRF middleware for vulnerable
cross-site, state-changing deployments and demonstrate `HttpOnly`, `Secure`,
and appropriate `SameSite` settings.

Signed and private cookie jars are not enabled in v0.5.5. JWT signatures already
provide token integrity; cookie encryption and non-JWT signed-cookie sessions
are separate features.

## Passport principals

The strategy returns an authenticated application principal, analogous to
NestJS Passport's `request.user`. It is distinct from signed token claims:

```text
UserClaims
  data carried inside and verified from the JWT

UserPrincipal
  current application identity returned by strategy validation
```

The public object-safe policy contract is:

```rust
pub trait PassportPrincipal: Send + Sync + 'static {
    fn has_role(&self, role: &str) -> bool;
    fn has_permission(&self, permission: &str) -> bool;
}
```

Applications may implement it manually. The derive supports named structs with
at most one `#[roles]` field and at most one `#[permissions]` field:

```rust
#[derive(PassportPrincipal)]
struct UserPrincipal {
    user_id: Uuid,
    email: String,
    #[roles]
    roles: Vec<String>,
    #[permissions]
    permissions: BTreeSet<String>,
}
```

Annotated collections must expose `.iter()` values implementing `AsRef<str>`.
An omitted role or permission field makes the corresponding method always
return false. Tuple structs, unions, duplicate marker fields, markers on the
wrong item, and incompatible field types fail compilation.

`ClaimsPrincipal<C>` is the built-in identity path for applications that want
to authorize directly from verified custom claims. It delegates role and
permission checks to `C: PassportPrincipal` and retains the full verified JWT.

`Authenticated<P>` is an Axum-compatible extractor for the principal installed
by a successful guard. A typed verified-claims extractor is available separately
when a handler needs token metadata. An unguarded route requesting either
extractor receives a typed rejection rather than an application panic.

## Passport strategies

A custom strategy is a managed provider and a trait implementation:

```rust
#[service]
struct AppJwtStrategy {
    users: UserService,
}

#[passport_strategy(name = "jwt")]
impl PassportStrategy for AppJwtStrategy {
    type Claims = UserClaims;
    type Principal = UserPrincipal;

    const TOKEN_KIND: JwtTokenKind = JwtTokenKind::Access;

    async fn validate(
        &self,
        context: &PassportContext<'_>,
        claims: &JwtClaims<Self::Claims>,
    ) -> PassportResult<Self::Principal> {
        // Resolve the current identity or reject authentication.
    }
}
```

`PassportStrategy` uses associated claim and principal types and a required
token kind. The strategy future must be `Send`. The trait itself is not used as
a trait object; `#[passport_strategy]` emits a type-erased descriptor and call
adapter for the concrete implementation. This preserves static eligibility and
supports async validation on Rust 1.85.

The macro accepts non-empty ASCII names containing lowercase letters, digits,
period, underscore, and hyphen. It verifies that the impl targets
`PassportStrategy` and emits the strategy's concrete type, claim type,
principal type, token kind, source location, and adapter. The strategy type must
also exist as a reachable managed provider; otherwise preflight emits `MADS130`.

`PassportContext` provides read-only access to request headers, method, URI,
and an optional remote address. Parsed-cookie access is present only with the
`cookies` feature. It does not allow a strategy to replace the route response
or bypass JWT verification. The framework verifies cryptography, registered
claims, and token kind before invoking `validate`.

The built-in strategy name is `jwt`. It maps verified claims into
`ClaimsPrincipal<C>`. A guard expecting another principal type must have one
reachable custom `jwt` strategy that produces that type.

Strategy resolution rules are:

1. One reachable custom strategy with a built-in name overrides the built-in.
2. Two reachable custom strategies with the same name are ambiguous.
3. Differently named strategies coexist.
4. A missing named strategy is a preflight failure.
5. A guard's declared principal must equal the selected strategy output.
6. v0.5.5 considers the complete static catalog.
7. v0.6.0 considers only root-module-reachable and legally exported entries.

`jwt-refresh` is not a built-in strategy. Applications define it when they want
a guarded refresh endpoint. It declares `JwtTokenKind::Refresh`, performs their
Redis/PostgreSQL/session validation, and returns their chosen principal. MADS
does not own refresh-token rotation or storage.

## Guard macro

`#[guard]` is legal on a MADS `#[routes]` trait and on methods inside that trait.
It is not legal on a controller struct, arbitrary function, or native Axum
handler.

Route-trait guards establish inherited defaults:

```rust
#[routes(prefix = "/users")]
#[guard(
    strategy = "jwt",
    principal = UserPrincipal,
    source = bearer,
    roles(any = ["user", "admin"]),
)]
trait UserRoutes {
    #[get("/profile")]
    #[guard(permissions(all = ["profile:read"]))]
    async fn profile(&self) -> HttpResult<Json<Profile>>;
}
```

The complete arguments are:

```text
strategy = "name"                         default: "jwt"
principal = RustType                      required unless inherited or skipped
source = bearer                           default: bearer
source = cookie("literal-name")
roles(any = ["role", ...])
roles(all = ["role", ...])
permissions(any = ["permission", ...])
permissions(all = ["permission", ...])
predicate = path::to::function
predicates = [path::one, path::two]
skip
```

`predicate` is shorthand for a one-element predicate list. A predicate has the
compile-time-checked signature:

```rust
fn(&Principal) -> bool
```

Predicates are synchronous application checks whose contract requires them to
be side-effect-free. Multiple predicates all have to return true. The type
system enforces the function signature, not purity. Database, Redis, or network
authorization belongs in a managed strategy or service.

Method-level guard values merge field by field. `strategy`, `principal`, and
`source` replace inherited values when present. A supplied roles, permissions,
or predicates clause replaces the corresponding inherited clause; unspecified
clauses remain inherited. Changing the principal while inheriting a predicate
whose signature uses the previous principal is a compile-time error.

Separate roles, permissions, and predicate clauses combine with AND. Within a
clause, `any` requires one value and `all` requires every value. Empty lists,
duplicate scalar arguments, both `any` and `all`, invalid cookie names, and
unknown arguments fail macro expansion.

`#[guard(skip)]` is valid only on a method inheriting a route-trait guard. It
cannot be combined with other guard arguments and removes the guard completely
for that method. Route-level `skip` and method-level `skip` without an inherited
guard are compile errors.

Cookie sources require the `cookies` feature. Using one without support emits a
focused compile-time diagnostic. One guard accepts one token source only; it
never falls back between a header and cookie.

## Guard runtime

The request path is fixed:

```text
select effective guard metadata
  -> extract exactly one Bearer or named cookie token
  -> reject oversized token
  -> select configured key without trusting token algorithm
  -> verify signature and registered claims
  -> enforce access/refresh token kind
  -> invoke selected managed strategy
  -> check principal roles
  -> check principal permissions
  -> evaluate principal predicates
  -> attach verified claims and principal to request extensions
  -> invoke controller method
```

Authentication runs after ordinary outer Tower middleware and before the route
handler's remaining extractors. No protected handler executes before a guard
succeeds.

Native Axum routes use a typed `PassportGuard<P>` builder/layer backed by the
same runtime. The procedural macro remains specific to MADS route traits. The
native API accepts the same strategy name, token source, roles, permissions,
and predicate paths and installs the same request extensions.

## Auto-configuration

The official descriptor identifier is:

```text
mads.common.passport.jwt
```

It outputs `JwtService`. Activation occurs when:

- any non-skipped effective guard exists; or
- any provider directly requires `JwtService`.

Every Passport guard requires `JwtService`, including guards with custom
strategies, because framework cryptographic verification precedes strategy
validation.

Evaluation follows the existing conditional-default rules:

1. An explicitly provided `JwtService` causes `OVERRIDDEN` before default
   configuration is parsed.
2. No requirement causes `SKIPPED`; unused Passport configuration is not parsed.
3. A requirement plus missing or invalid configuration causes `FAILED`.
4. Valid required configuration causes `ACTIVE`.
5. Evaluation is side-effect-free except for read-only configured key-file
   access and performs no network operation.
6. Key objects are constructed only after combined graph validation succeeds.

Providing an explicit value of the concrete `JwtService` type is ordinary
conditional-default back-off: it selects `OVERRIDDEN` but does not replace the
service API or cryptographic implementation polymorphically. Application
authentication polymorphism belongs to `PassportStrategy`; v0.6.0 adds module
eligibility to those strategy overrides.

The auto-configuration report includes guard requirements alongside provider
requirements. Guard requirement subjects use the stable route trait and method
name plus source location. Configuration evidence contains key names and source
labels only.

## Startup and preflight ordering

The v0.5.5 build order is:

```text
explicit configuration
  -> complete provider, route, guard, and strategy catalogs
  -> route/method guard merge and syntax validation
  -> strategy name and principal-type validation
  -> JWT auto-configuration evaluation
  -> virtual application graph validation
  -> selected JwtService/key-ring application
  -> ordinary provider and strategy construction
  -> route validation and guarded router construction
  -> infrastructure lifecycle
  -> application lifecycle
  -> existing explicit bind
```

Missing strategies, duplicate strategy names, principal mismatches, missing JWT
configuration, malformed keys, and invalid effective guards fail before
ordinary provider construction. Invalid routes continue to fail before
lifecycle startup and binding. v0.5.5 does not change the explicit listener API.

## Errors and HTTP mapping

### Diagnostic codes

```text
MADS110  cookie parsing or response-cookie validation
MADS120  JWT configuration-independent signing, verification, or key operation
MADS121  JWT auto-configuration evaluation or application
MADS130  Passport strategy registration, resolution, or type mismatch
MADS131  guard metadata or authentication-policy failure
```

### Typed runtime errors

`JwtError` is non-exhaustive and exposes a typed kind covering:

- invalid configuration;
- unreadable or malformed key material;
- unavailable signing key;
- serialization and deserialization;
- malformed or oversized token;
- disallowed or mismatched algorithm;
- missing or unknown `kid`;
- invalid signature;
- missing or expired `exp`;
- invalid `nbf`;
- issuer, audience, subject, or JWT ID mismatch;
- header/claim token-kind mismatch.

`PassportError` distinguishes an expected authentication rejection from an
operational strategy failure. Strategies use explicit constructors/variants for
`reject` and `internal`; an application database outage cannot silently become
an invalid-credentials response.

HTTP mapping is:

| Condition | Response |
| --- | --- |
| Missing, malformed, invalid, expired, or wrong-kind token | `401 Unauthorized` |
| Strategy rejects identity | `401 Unauthorized` |
| Role, permission, or predicate fails | `403 Forbidden` |
| Strategy or framework operational error | `500 Internal Server Error` |
| Malformed ordinary cookie extraction | `400 Bad Request` |

Authentication failures include a generic `WWW-Authenticate: Bearer` header.
Responses do not expose token-validation details. Application code can inspect
typed errors and source chains.

## Secret handling

The following values are sensitive and never occur in `Display`, `Debug`,
diagnostics, reports, startup summaries, or guard responses:

- HMAC secrets;
- private and public key contents;
- resolved tokens;
- custom and registered claim values;
- cookie names and values held by a jar;
- resolved configuration values.

Key IDs, algorithm names, configuration keys, source labels, strategy names,
and source locations are safe evidence. Paths can be diagnostic subjects only
after credential-like URL material is redacted; key contents are never source
text.

## v0.6.0 compatibility contract

v0.5.5 establishes strategy descriptors using concrete provider, claims, and
principal type IDs plus names and source locations. v0.6.0 scopes those
descriptors through the root `AppModule` provider set.

The v0.6 rules are:

- a strategy must implement `PassportStrategy` and carry
  `#[passport_strategy]` metadata;
- its concrete strategy type must be a managed provider;
- its owning module must be reachable from the root module;
- cross-module use must satisfy provider export/visibility rules;
- only eligible and visible strategies participate in name resolution;
- one visible custom strategy overrides the built-in name;
- multiple visible custom strategies with one name are ambiguous;
- providers remain inferred and are not manually repeated in module manifests.

No module behavior ships in v0.5.5. The strategy API and descriptors are shaped
so v0.6 adds scoping rather than changing application authentication code.

## Acceptance criteria

Version 0.5.5 is complete only when:

1. `[passport] secret = "${JWT_SECRET}"` resolves through the existing explicit
   ConfigBuilder/dotenv flow and produces an HS256-only `JwtService` when JWT is
   required.
2. Unused Passport configuration is skipped and unparsed.
3. Every required HS, RS, and ES algorithm signs and verifies correctly.
4. Token headers never select an algorithm outside the configured allowlist.
5. Each configured key is bound to one algorithm.
6. Named key rotation signs with the active key and verifies retained previous
   keys through `kid`.
7. Inline and file-backed RSA/EC keys work with deterministic path resolution.
8. Weak HMAC keys and malformed key material fail startup safely.
9. Expiration is mandatory; not-before, issuer, audience, subject, and clock
   skew obey the specified policy.
10. Access and refresh tokens have mutually exclusive header and claim types.
11. Refresh-token persistence and rotation remain user logic.
12. `JwtService` exposes typed sign/verify plus explicitly unverified decode
    APIs.
13. Route-trait guards inherit to methods and method values override fields
    without losing unrelated inherited policy.
14. `#[guard(skip)]` provides an explicit, validated inherited-policy opt-out.
15. Roles, permissions, and principal predicates produce deterministic `403`
    decisions after authentication.
16. Missing/invalid authentication and strategy rejection produce generic
    `401`; operational failures produce `500`.
17. Custom strategy registration is trait-checked, managed, deterministic, and
    explainable.
18. One custom strategy overrides a built-in name; duplicates fail preflight.
19. Cookie request parsing and `Set-Cookie` response composition cover every
    required attribute.
20. Cookie-sourced guards reject missing, malformed, and duplicate target
    cookies.
21. Native Axum routes retain cookie and Passport escape hatches.
22. Secrets, tokens, claims, cookie values, and key contents never leak through
    framework diagnostics, reports, or debug output.
23. Feature combinations preserve core-only and JWT-only dependency boundaries.
24. v0.5.5 does not implement CORS, HTTP auto-binding, CSRF, remote JWKS, or
    module scoping.
25. The workspace passes formatting, lint, test, documentation, MSRV,
    architecture, and coverage gates.

## Resolved decisions

- The change is architectural and uses the existing official
  auto-configuration engine.
- Passport/JWT and cookies live in feature-gated `mads-common` modules.
- `jsonwebtoken` 10.3.0 with RustCrypto is pinned for Rust 1.85.
- Configuration loading remains explicit.
- The generic engine gains real string arrays while scalar APIs remain
  compatible.
- Simple `passport.secret` means HS256 only.
- Weak secrets are errors.
- Algorithms are application allowlists, never trusted token choices.
- Key rotation uses one active signer and multiple verification keys.
- PEM content and paths are both supported and mutually exclusive per field.
- `exp` is mandatory; configured issuer/audience checks cannot be weakened.
- Token lifetimes and kinds are explicit at every sign call.
- Access and refresh JWTs use MADS-private explicit types.
- Refresh persistence, rotation, revocation, and replay detection are user logic.
- JWT verification always precedes application strategy validation.
- Strategies return current typed principals rather than exposing raw claims as
  authenticated users.
- Custom strategy eligibility is a Rust trait plus macro-generated descriptor.
- Guards live on route traits and methods, not controllers.
- Route guards inherit; method guards override specified fields.
- `skip` is the explicit public-route escape hatch.
- One token source is selected per guard; Bearer is the default.
- Cookie guards require cookie feature support.
- Roles and permissions have explicit any/all semantics.
- Predicates are synchronous principal-only functions.
- Cookie authentication and CSRF protection remain separate concerns.
- CORS and HTTP auto-binding move to v0.5.6.

> **Roadmap supersession (v0.6.0):** The planned v0.5.6 CORS and HTTP
> auto-binding milestone was merged into v0.6.0 so it could share the root
> module scope with provider, route, guard, and strategy discovery.

- v0.6 adds module scoping to stable v0.5.5 strategy metadata.

There are no unresolved design decisions in this specification.
