# MADS.rs v0.5.0 Auto-Configuration Specification

**Date:** 2026-08-23
**Status:** Approved design
**Milestone:** 0.5.0

## Problem statement

MADS.rs 0.4 has deterministic dependency injection and explicit
PostgreSQL/Diesel persistence, but the two systems are not connected
automatically. Provider macros already declare dependencies and the core graph
already discovers, validates, and constructs those providers. When a repository
declares a `Database` field, however, an application must still parse
`DatabaseConfig`, construct `DatabaseBootstrap`, and call the database builder
extension itself.

Version 0.5 adds an explainable conditional-default layer between catalog
discovery and graph validation:

```text
application requirement
        +
linked official capability
        +
resolved configuration
        ↓
auto-configuration decision
        ↓
default provider and infrastructure lifecycle
```

The first vertical slice is Diesel database provisioning. The engine belongs
to `mads-core`; the database-specific conditions and provisioning belong to
`mads-common`. Core must remain free of Diesel, PostgreSQL, pool, migration,
HTTP, and `mads-common` dependencies.

The feature must preserve the existing DI model. Auto-configuration does not
replace `#[service]`, `#[repository]`, `#[provider]`, provider graph analysis,
or deterministic construction. It conditionally fills a missing infrastructure
type before the ordinary provider plan executes.

## Goals

1. Add a reusable, deterministic engine for official MADS
   auto-configurations.
2. Keep public DI declaration and construction behavior unchanged.
3. Automatically provide `mads_common::Database` when all of these are true:
   - a discovered provider directly requires `Database`;
   - the official Diesel integration is linked; and
   - valid database configuration is available.
4. Back off completely when an application owns the `Database` provider.
5. Preserve side-effect-free `MadsBuilder::analyze()` behavior while exposing
   every auto-configuration decision.
6. Retain the decisions used by a successful application for future
   diagnostics and `mads doctor` rendering.
7. Distinguish auto-configured providers from application-provided and
   statically declared providers in graph inspection.
8. Support optional embedded startup migrations without requiring explicit
   database pool bootstrap.
9. Start framework infrastructure before application lifecycle hooks and stop
   it after application hooks.
10. Preserve deterministic results independently of inventory registration,
    crate link, hash-map, or application hook registration order.
11. Keep existing public persistence, configuration, HTTP, and CLI contracts
    compatible.

## Non-goals

Version 0.5 does not add:

- automatic loading of `.env`, `mads.toml`, or `MADS_*` variables from
  `Mads::builder()`;
- a supported application or third-party auto-configuration registration API;
- chained or cascading auto-configurations;
- priority-based selection between conflicting defaults;
- module-aware reachability, module ownership, imports, exports, or visibility
  enforcement;
- HTTP host/port configuration, automatic listener binding, CORS, cookies, or
  authentication;
- `mads doctor` or another new diagnostic CLI renderer;
- migration SQL generation or automatic schema diffing;
- proactive pending-migration or schema checks when startup migration is
  disabled;
- MySQL, SQLite, a backend-generic database facade, or another persistence
  implementation;
- request validation, application/domain error policy, or automatic mapping of
  database errors into HTTP responses;
- a general auto-configuration opt-out flag, `database.enabled`, or per-entry
  exclusions; or
- dependency upgrades unrelated to the 0.5 feature.

HTTP auto-binding is assigned to v0.5.5. Module scoping is assigned to v0.6.
Detailed configuration provenance remains v0.7 work. `mads doctor` remains
v0.8 work.

## Constraints

- The workspace remains Rust edition 2024 with MSRV Rust 1.85.0.
- All crate source keeps `#![forbid(unsafe_code)]`; public APIs remain fully
  documented under `#![deny(missing_docs)]`.
- `mads-core` has no normal dependency on Diesel, `deadpool-diesel`,
  `diesel_migrations`, PostgreSQL client libraries, Axum, or `mads-common`.
- PostgreSQL is the sole database backend in v0.5.
- Diesel remains pinned to `=2.2.12`, `diesel_migrations` to `=2.2.0`, and
  `deadpool-diesel` to `=0.6.1`.
- The existing `common` Cargo feature represents availability of the official
  HTTP and Diesel integration. v0.5 introduces no database-specific feature
  split.
- Auto-configuration must not make `mads-core` depend on process environment,
  filesystem conventions, network state, or database connectivity.
- Analysis invokes no provider constructor, auto-configuration apply callback,
  pool constructor, connection attempt, migration, or lifecycle hook.
- Auto-configuration reports never retain or display resolved configuration
  values.
- Existing error sources remain preserved rather than flattened into strings.
- Existing CLI exit codes and output remain unchanged.
- CI continues to enforce PostgreSQL 16 integration suites and at least 85%
  line coverage.

## Approaches considered

### Chosen: two-phase official auto-configuration registry

`mads-core` collects official descriptors, evaluates them before graph
validation, and produces reports plus virtual provider satisfactions. A public
analysis stops there. A build applies active decisions only after the combined
analysis is valid, then runs the ordinary provider construction plan.

This approach fits the existing inventory-based metadata model, preserves the
core/common boundary, keeps analysis side-effect-free, and lets v0.6 substitute
a root-module-scoped catalog without redesigning the engine.

The cost is a two-phase contract. Evaluation and application must be tested for
parity so an integration cannot evaluate as active and then apply different
conditions.

### Rejected: conditional providers inside `ProviderDescriptor`

This would place conditional selection, configuration evidence, default
precedence, and lifecycle installation inside ordinary DI provider metadata.
It would unify construction superficially, but would complicate existing
duplicate, ambiguity, satisfaction-state, and constructor semantics. It would
also force infrastructure lifecycle behavior into a descriptor that currently
has one clear responsibility.

### Rejected: database-specific builder preprocessing

The facade or common crate could special-case database registration before core
graph analysis. That is smaller for one integration but does not create the
reusable v0.5 engine promised by the timeline. It would also make later
official integrations and v0.6 scoped evaluation harder to integrate
consistently.

## Architectural boundaries

The final ownership model is:

```text
application code
  ├── explicitly builds Config
  ├── declares providers and their dependencies
  └── optionally registers one embedded migration source
                         │
                         v
mads-core
  ├── discovers provider and official auto-configuration metadata
  ├── evaluates conditions and produces inspection reports
  ├── validates a graph with virtual default satisfactions
  ├── applies active official defaults after validation
  ├── constructs ordinary providers
  └── orders infrastructure and application lifecycle hooks
                         │
                         v
mads-common
  ├── declares the official Diesel database auto-configuration
  ├── parses DatabaseConfig
  ├── creates and owns the Database pool
  ├── supplies the database lifecycle hook
  └── applies registered embedded migrations when enabled
```

`mads` remains the application facade. `mads-extra` is unchanged.

## Terminology

An **application requirement** is a direct dependency declared by a provider
descriptor in the catalog used for the current build. In v0.5 that catalog is
the complete statically discovered provider catalog. A provider does not need
to be reachable from an HTTP route to contribute a requirement. Version 0.6 may
replace the complete catalog with the subset reachable from a root
`AppModule`.

An **official capability** is an auto-configuration descriptor linked from an
official MADS integration crate. The Diesel capability is available when
`mads-common` is compiled and linked through the existing `common` feature.
There is no runtime probe. An integration that is not linked has no descriptor
and therefore no report; core does not synthesize records for absent crates.

A **user override** is any application-controlled provider for the exact output
type of an auto-configuration. For `Database`, this includes:

- `MadsBuilder::provide(Database)`;
- `MadsBuilder::construct::<Database>()` after successful construction;
- `MadsBuilderDatabaseExt::database(DatabaseBootstrap)`; and
- a static `#[provider]` whose output is `Database`.

An **auto-configured provider** is a value inserted by an active official
auto-configuration after successful combined analysis and before ordinary
provider construction.

## Public inspection model

`mads-core` adds a public status enum:

```rust
#[derive(Clone, Copy, Debug, Eq, Hash, PartialEq)]
pub enum AutoConfigurationStatus {
    Active,
    Skipped,
    Overridden,
    Failed,
}
```

Rust variants use normal casing. Human and CLI rendering uses the uppercase
forms `ACTIVE`, `SKIPPED`, `OVERRIDDEN`, and `FAILED`.

Reason identifiers use a stable string wrapper analogous to
`DiagnosticCode`:

```rust
#[derive(Clone, Copy, Debug, Eq, Hash, PartialEq)]
pub struct AutoConfigurationReasonCode(&'static str);

impl AutoConfigurationReasonCode {
    pub const fn as_str(self) -> &'static str;
}
```

The initial stable reason strings are:

| Reason | Status | Meaning |
| --- | --- | --- |
| `conditions_matched` | `ACTIVE` | Every condition matched and the default is selected. |
| `requirement_absent` | `SKIPPED` | No catalog provider directly requires the output. |
| `user_override` | `OVERRIDDEN` | An application-controlled provider owns the output. |
| `missing_configuration` | `FAILED` | A required integration key is absent. |
| `invalid_configuration` | `FAILED` | A required integration value cannot be parsed or validated. |
| `missing_migration_source` | `FAILED` | Startup migration is enabled without embedded migrations. |
| `provisioning_failed` | `FAILED` | Applying an otherwise valid default failed before application construction. |
| `duplicate_identifier` | `FAILED` | Official descriptors reused one stable identifier. |
| `conflicting_default` | `FAILED` | Multiple active official defaults target one output type. |

Public evidence is split into focused immutable records:

```rust
pub struct AutoConfigurationRequirement {
    // provider type name and optional declaration location
}

pub struct AutoConfigurationConfigEvidence {
    // configuration key and optional existing Config source label
}

pub struct AutoConfigurationReport {
    // identifier
    // output type name
    // status
    // reason code
    // human-readable explanation
    // sorted direct requirements
    // configuration evidence
}
```

Each type exposes read-only accessors. Reports never expose `TypeId`, callback
addresses, resolved configuration values, URLs, credentials, dotenv values, or
process-variable values.

Configuration evidence preserves the v0.4 attribution model. A
`database.url = "${DATABASE_URL}"` value read from `mads.toml` continues to
attribute the configuration key to `mads.toml`; v0.5 does not distinguish
whether interpolation came from `.env` or the process environment. A direct
`MADS_DATABASE__URL` override loaded through `EnvSource` retains that source's
existing label.

Reports are exposed in deterministic descriptor order through:

```rust
impl GraphAnalysis {
    pub fn auto_configurations(&self) -> &[AutoConfigurationReport];
}

impl Mads {
    pub fn auto_configurations(&self) -> &[AutoConfigurationReport];
}
```

`GraphAnalysis` reports what a build would select without applying it. A
successful `Mads` retains the reports used for that build. If application of an
active default fails, `build()` returns its diagnostic and no `Mads` exists;
the failure is represented by `MADS101` and the `provisioning_failed` reason in
the diagnostic text. A prior side-effect-free analysis may have reported the
entry as active because application is deliberately outside analysis.

## Provider graph representation

The graph model gains explicit variants:

```rust
pub enum ProviderOrigin {
    Provided,
    AutoConfiguration,
    Service,
    Repository,
    Provider,
}

pub enum ProviderState {
    Provided,
    Preconstructed,
    AutoConfigured,
    Planned,
}
```

An active decision adds a virtual `AutoConfigured` satisfaction during graph
analysis. The virtual node has `ProviderOrigin::AutoConfiguration`, public
visibility, no application source location, and no declared provider
dependencies. The real value is not inserted until a valid build applies the
decision.

This explicit representation prevents `mads graph` and diagnostics from
mislabeling a framework default as an application-provided value.

## Official registration contract

Core defines a public-but-document-hidden contract because `mads-common` is a
separate crate. It is not re-exported through the application prelude and is
not a supported third-party API in v0.5.

One internal descriptor contains:

- a globally stable identifier;
- its output type name and runtime type identifier;
- deterministic source metadata for invalid-catalog diagnostics;
- a side-effect-free evaluator; and
- an apply callback for a selected decision.

`inventory` collects descriptors. Core canonicalizes them by identifier,
output type name, and source location before validation. Inventory registration
or crate link order never affects evaluation.

Official registration identifiers use reverse ownership segments. The v0.5
database descriptor is:

```text
mads.common.database.diesel
```

Duplicate identifiers produce one deterministic `MADS007` diagnostic and a
failed `duplicate_identifier` report for that identifier. Duplicate groups are
not evaluated.

After evaluation, if two active descriptors target the same output type, both
are converted to failed `conflicting_default` reports and graph analysis
receives one deterministic `MADS007` conflict diagnostic. The engine never
selects by priority. A user override precedes this check and therefore backs
off every official default for that type.

## Evaluation context and ordering

An evaluator receives read-only access to:

- the resolved `Config` already owned by `MadsBuilder`;
- the complete provider descriptor catalog used by the build;
- builder satisfactions created by `provide` and `construct`;
- official integration inputs registered on the builder; and
- stable type and source metadata needed for evidence.

It cannot mutate the provider registry, lifecycle manager, configuration,
catalog, or process environment.

Each valid descriptor evaluates exactly once per analysis in lexical identifier
order. v0.5 performs one pass. An auto-configured output is not added to another
descriptor's requirement input, so one auto-configuration cannot activate
because another auto-configuration introduced a dependency.

The engine uses this decision order for each descriptor:

1. Detect application-controlled outputs.
2. If any exist, record `OVERRIDDEN` with `user_override` and stop evaluating
   that descriptor.
3. Otherwise collect every direct catalog dependency on the output.
4. If none exist, record `SKIPPED` with `requirement_absent` and stop.
5. Validate the integration's required configuration.
6. Validate any registered integration input required by that configuration.
7. Record `FAILED` for a condition failure or `ACTIVE` when all conditions
   match.

Override has precedence over absent requirement. A supplied `Database` with no
consumers therefore reports `OVERRIDDEN`, not `SKIPPED`. An unused invalid
`[database]` section is not parsed when there is no override and no database
requirement. An override also prevents parsing or validation of default
database configuration.

Every direct requiring provider is retained in deterministic type-name and
source-location order. The engine does not choose or display only the first
consumer.

## Combined analysis and diagnostic aggregation

`MadsBuilder::analyze()` performs these operations:

```text
read immutable builder inputs
        ↓
validate and sort official descriptors
        ↓
evaluate official conditions
        ↓
resolve active-default conflicts
        ↓
add virtual AutoConfigured satisfactions
        ↓
analyze the ordinary provider graph
        ↓
merge auto-configuration and graph diagnostics
        ↓
return GraphAnalysis with graph, optional plan, diagnostics, and reports
```

No step invokes an apply callback or provider constructor.

If an auto-configuration failed for an output that the catalog requires, graph
analysis suppresses the redundant `MADS003` for that same missing output.
`MADS101` already explains why the framework could not supply it. Unrelated
missing dependencies, duplicate providers, cycles, and other graph diagnostics
remain present and retain their existing deterministic ordering.

A custom output never hides normal graph failures. Multiple static
`Database` providers cause the auto-configuration to report `OVERRIDDEN` and
the provider graph to return `MADS002`. A self-dependent custom provider can
still return `MADS005`.

No construction plan is exposed when the combined diagnostics are non-empty.

## Build and application flow

`MadsBuilder::build()` uses the same evaluation implementation as public
analysis. Its flow is:

```text
evaluate conditions and build reports
        ↓
simulate active outputs and validate the graph
        ↓
stop on any combined diagnostic
        ↓
apply active defaults in stable identifier order
        ↓
insert real AutoConfigured values and infrastructure hooks
        ↓
execute the already validated ordinary construction plan
        ↓
return Mads with graph, construction plan, and reports
```

Application of active defaults happens only after the complete simulated graph
is valid. An unrelated graph failure therefore prevents pool construction and
ordinary provider construction.

Application happens before the first ordinary provider constructor, so a
repository can resolve the real `Database` value when its construction step
runs. An application failure returns its integration diagnostic and prevents
all ordinary provider constructors.

The builder's `Config` and integration inputs are immutable across evaluation
and application. Integrations must share condition-validation functions
between both phases. Parity tests prove that application does not reinterpret
conditions differently.

## Lifecycle ordering

`LifecycleManager` distinguishes two hook groups:

1. official framework infrastructure hooks; and
2. application hooks registered through the existing public builder API.

Infrastructure hooks have an owning stable identifier. Startup order is:

```text
infrastructure hooks by identifier
        ↓
application hooks by registration order
```

Shutdown and startup rollback use the exact reverse order of hooks that
successfully started. Therefore:

- the database is ready before application startup hooks;
- application shutdown hooks may continue using the database;
- the database closes only after application hooks stop; and
- failure in a later application hook rolls back earlier application hooks and
  then infrastructure.

The cross-crate infrastructure-hook registration function is document-hidden
and reserved for official integrations. Public `MadsBuilder::lifecycle_hook`
continues to register application hooks in caller order.

`MadsBuilderDatabaseExt::database(DatabaseBootstrap)` registers its database
hook in the infrastructure group even though the database provider was chosen
explicitly. A custom `Database` value or static provider receives no framework
database hook; the application owns its readiness, migration, and closure
policy.

Existing HTTP preflight order remains:

```text
build and validate provider graph
        ↓
apply defaults and construct application
        ↓
build and validate router
        ↓
start lifecycle
        ↓
bind listener
```

Pool construction does not connect. Invalid routes can cause an allocated pool
value to be dropped, but they cause no database checkout, readiness query,
migration, application hook, or listener bind.

## Diesel database auto-configuration

`mads-common` supplies the official descriptor with this contract:

```text
identifier:  mads.common.database.diesel
output:      mads_common::Database
requirement: any catalog provider directly depends on Database
capability:  descriptor is linked through mads-common/common feature
config:      database.url, database.pool_size, database.migrate
input:       optional EmbeddedMigrations
```

The integration evaluates user override before reading any database
configuration. A custom provider therefore wins even if the default
`database.url` is missing, unresolved, malformed, or otherwise invalid.

With a real requirement and no override, evaluation calls the same typed
database configuration validation used by explicit bootstrap. The configuration
contract remains:

```toml
[database]
url = "${DATABASE_URL}"
pool_size = 10
migrate = false
```

- `database.url` is required, non-empty, and already interpolated.
- `database.pool_size` defaults to `10` and must be a positive integer.
- `database.migrate` defaults to `false` and must be `true` or `false`.
- Existing dotenv, process environment, and ordered source precedence remain
  unchanged.

Missing or invalid configuration produces a failed report and `MADS101`. Every
direct provider requiring `Database` appears in the evidence and diagnostic.

On application, the integration:

1. reconstructs the already validated `DatabaseConfig` from the immutable
   builder config;
2. creates the deadpool-diesel PostgreSQL pool without connecting;
3. inserts `Database` with auto-configured provider metadata; and
4. installs one database infrastructure lifecycle hook.

Pool-construction failure produces `MADS101` with the preserved
`DatabaseError` source and prevents ordinary provider construction.

## Application bootstrap examples

Configuration remains explicit in v0.5. With startup migrations disabled,
database-specific bootstrap disappears:

```rust,ignore
use mads::{
    core::{ConfigBuilder, DotenvSource, EnvSource, TomlSource},
    prelude::*,
};

let config = ConfigBuilder::new()
    .dotenv(DotenvSource::optional(".env"))
    .source(TomlSource::file("mads.toml"))
    .source(EnvSource::new("MADS_"))
    .build()?;

let application = Mads::builder_with_config(config).build().await?;
```

This is **zero database bootstrap**, not zero application configuration. Calling
`Mads::builder()` still supplies empty configuration. If a provider requires
`Database`, the linked Diesel default then fails with `MADS101` because
`database.url` is absent.

An application that enables startup migration registers only its embedded
source:

```rust,ignore
use mads::{
    core::{ConfigBuilder, DotenvSource, EnvSource, TomlSource},
    diesel_migrations::{EmbeddedMigrations, embed_migrations},
    prelude::*,
};

const MIGRATIONS: EmbeddedMigrations = embed_migrations!("migrations");

let config = ConfigBuilder::new()
    .dotenv(DotenvSource::optional(".env"))
    .source(TomlSource::file("mads.toml"))
    .source(EnvSource::new("MADS_"))
    .build()?;

let mut builder = Mads::builder_with_config(config);
builder.database_migrations(MIGRATIONS)?;
let application = builder.build().await?;
```

`DatabaseBootstrap` remains available as the explicit escape hatch:

```rust,ignore
let database = DatabaseConfig::from_config(&config)?;
let mut builder = Mads::builder_with_config(config);
builder.database(
    DatabaseBootstrap::new(database).with_migrations(MIGRATIONS),
)?;
let application = builder.build().await?;
```

This last form reports the official default as overridden and preserves the
explicit v0.4 behavior.

## Embedded migration registration

The existing `MadsBuilderDatabaseExt` gains:

```rust
fn database_migrations(
    &mut self,
    migrations: diesel_migrations::EmbeddedMigrations,
) -> mads_core::Result<&mut Self>;
```

The method records integration input; it does not create a pool, connect, or
run migrations. At most one application-wide embedded source may be
registered. A second registration returns deterministic `MADS101` rather than
merging sources or choosing by order.

When `database.migrate = true`, an active database default requires this
source. Its absence produces `missing_migration_source` and `MADS101` during
analysis. When migration is false, a registered source is accepted and the
report states that startup migration is disabled.

If a custom provider overrides the default, the separately registered source
is unused. The default does not install a partial migration hook around a
custom database.

Version 0.5 preserves embedded startup migrations. It does not read a runtime
`migrations/` directory during application startup and does not invoke or
embed `diesel_cli`.

## Migration runtime behavior

The active database lifecycle keeps the v0.4 sequence:

```text
resolve Database
        ↓
check PostgreSQL readiness
        ↓
if database.migrate = true, run pending embedded migrations
        ↓
allow later lifecycle hooks and listener binding
```

Diesel's migration harness compares embedded migration versions with its
database migration records. Existing pending files are applied. If all
versions are already applied, startup migration succeeds without doing work.

MADS never generates `up.sql` or `down.sql`, never derives a migration from
`schema.rs`, and never applies generated, unreviewed SQL. The existing
`mads db migrate`, `mads db rollback`, and `mads db status` commands continue
to use file migrations and retain their current output and exit codes.

When `database.migrate = false`, MADS neither applies nor proactively checks
pending migrations. A later missing-table, missing-column, or other schema
query failure remains a structured `DatabaseError::Query`; the application
chooses its domain and HTTP policy.

## Back-off behavior

Back-off covers the complete database default, not only provider insertion.
When an override exists, the Diesel auto-configuration does not:

- parse or validate default database configuration;
- create a pool;
- register readiness or migration behavior;
- close the user-owned database during shutdown; or
- normalize its operational errors.

A single static `#[provider]` returning `Database` is a valid override and is
constructed through the ordinary graph plan. Two or more static providers for
`Database` cause `OVERRIDDEN` plus the existing `MADS002`; the auto-configuration
never picks one. A builder-provided or preconstructed value continues to
satisfy one matching static descriptor under current graph semantics; an
already ambiguous static catalog remains ambiguous.

## Status behavior

The Diesel entry uses these exact outcomes:

| Situation | Status | Reason | Configuration read? | Default applied? |
| --- | --- | --- | --- | --- |
| Any user-controlled `Database` exists | `OVERRIDDEN` | `user_override` | No | No |
| No override and no provider requires `Database` | `SKIPPED` | `requirement_absent` | No | No |
| Requirement exists and `database.url` is missing | `FAILED` | `missing_configuration` | Yes | No |
| Requirement exists and database configuration is invalid | `FAILED` | `invalid_configuration` | Yes | No |
| Migration is enabled and no embedded source is registered | `FAILED` | `missing_migration_source` | Yes | No |
| All conditions match | `ACTIVE` | `conditions_matched` | Yes | During build |
| Valid selection cannot create its pool | build error | `provisioning_failed` in `MADS101` | Yes | No |

If both override and absent requirement are true, `OVERRIDDEN` wins.

`FAILED` covers condition evaluation and application only. Once a successful
application retains `ACTIVE`, readiness or migration execution does not mutate
the report.

## Diagnostics and error preservation

Core adds:

```rust
/// Official auto-configuration registry or selection failure.
pub const MADS007: DiagnosticCode = DiagnosticCode::new("MADS007");
```

The database module adds and the facade re-exports:

```rust
/// Diesel database auto-configuration failure.
pub const MADS101: DiagnosticCode = DiagnosticCode::new("MADS101");
```

Diagnostic ownership is:

| Code | Owner | Meaning in v0.5 |
| --- | --- | --- |
| `MADS007` | `mads-core` | Duplicate official identifier or conflicting active defaults. |
| `MADS101` | `mads-common` | Database auto-configuration condition or application failed. |
| `MADS100` | `mads-common` | Explicit database bootstrap, readiness, or migration runtime failed. |
| `MADS011` | `mads-core` | Outer lifecycle hook failure context. |

Missing configuration diagnostics name `database.url`, list every direct
requiring provider, and suggest providing configuration or an explicit/custom
`Database`. Invalid configuration retains `DatabaseError` as its source when
one exists. Pool creation preserves its database error source.

Readiness and migration errors occur after the default is active. They keep the
existing inner `MADS100` and outer `MADS011` structure. The database hook closes
its own pool before returning a startup failure because the generic lifecycle
manager records a hook as started only after its start method succeeds.

No diagnostic, source display, `Debug` implementation, or report exposes the
database URL.

## Failure ordering and side effects

Required ordering guarantees are:

1. Invalid official descriptor registration prevents evaluation.
2. Auto-configuration conditions and graph validation run before default
   application.
3. Any combined analysis diagnostic prevents pool construction and all
   ordinary provider constructors.
4. Pool construction failure prevents all ordinary provider constructors.
5. Provider construction failure occurs before route validation, as in v0.4.
6. Route validation failure prevents database checkout, readiness, migration,
   lifecycle startup, and listener binding.
7. Database readiness or migration failure prevents application hooks and
   listener binding.
8. Failure in a later lifecycle hook rolls back successfully started hooks in
   reverse order.
9. Bind or serving failure after successful startup still shuts down
   application hooks and then infrastructure.

Pool creation is not a connection attempt. Dropping an application or failed
serve future before lifecycle startup releases the pool value without running
startup behavior.

## Component and file boundaries

The implementation uses focused modules:

```text
crates/mads-core/src/auto_configuration/mod.rs
    public exports and official inventory collection

crates/mads-core/src/auto_configuration/report.rs
    public status, reason, evidence, and report records

crates/mads-core/src/auto_configuration/descriptor.rs
    document-hidden official descriptor, evaluation, and application contracts

crates/mads-core/src/auto_configuration/analysis.rs
    sorting, condition evaluation, conflicts, virtual satisfactions, diagnostics

crates/mads-core/src/builder.rs
    combined analysis, valid-default application, retained reports

crates/mads-core/src/graph/model.rs
    auto-configured provider origin and state

crates/mads-core/src/lifecycle.rs
    infrastructure/application hook grouping and ordering

crates/mads-common/src/database/auto_configuration.rs
    Diesel descriptor, conditions, apply behavior, migration input registration

crates/mads-common/src/database/lifecycle.rs
    shared database hook and preserved explicit bootstrap
```

Existing database `config`, `pool`, `migration`, and `error` modules remain the
single owners of their established responsibilities. The new integration must
reuse them rather than duplicate parsing, pool, migration, or error logic.

The facade re-exports application-facing report types, graph variants,
`MADS007`, `MADS101`, and the extended database builder trait. It does not
re-export the internal descriptor contract through `prelude`.

## Testing strategy

### Core unit and integration tests

Core tests cover:

- status and reason-code accessors and rendering;
- lexical descriptor ordering independent of input order;
- duplicate identifier detection;
- conflict detection for two active defaults targeting one type;
- user override precedence over requirements and configuration;
- absent-requirement skipping without configuration access;
- one-pass behavior with no cascading activation;
- complete-catalog direct requirement discovery;
- deterministic sorting of every requiring provider;
- virtual graph satisfaction and explicit origin/state;
- suppression of redundant `MADS003` with preservation of unrelated graph
  diagnostics;
- unchanged `MADS002` and `MADS005` behavior for invalid custom providers;
- zero evaluator application, provider construction, pool creation, lifecycle,
  or other side effects during `analyze()`;
- apply-before-provider-construction ordering after valid analysis;
- application failure before ordinary provider constructors;
- report retention in successful applications;
- infrastructure hook ordering by identifier;
- application hook ordering by registration;
- reverse shutdown and rollback across both groups; and
- stable, MSRV-compatible, documented public APIs.

Test-only descriptor analysis helpers accept explicit descriptor slices so
tests do not depend on the process-global inventory contents.

### Database offline tests

`mads-common` tests cover:

- no requirement plus missing or invalid configuration is `SKIPPED`;
- every supported override form is `OVERRIDDEN`;
- an override ignores invalid default configuration and registered migration
  input;
- one requirement plus missing URL is `MADS101`, not `MADS003`;
- invalid pool size, migration boolean, unresolved URL, and invalid pool
  construction preserve their source and use `MADS101`;
- every direct requiring provider appears in stable order;
- migration enabled without a source is `MADS101`;
- one migration source registers without creating a pool;
- duplicate migration source registration is `MADS101`;
- a source with migration disabled is accepted and not run;
- auto-configured graph origin and state are correct;
- explicit `DatabaseBootstrap` remains an override and keeps its v0.4 behavior;
- custom database providers receive no framework lifecycle hook;
- debug and report output redact URLs and configuration values; and
- database CLI parsing, output, and exit behavior remain unchanged.

### PostgreSQL integration tests

With `MADS_TEST_DATABASE_URL` targeting PostgreSQL 16, tests prove:

1. A repository requiring `Database` builds and performs CRUD without
   `DatabaseBootstrap` or `builder.database(...)`.
2. The auto-configured pool is shared through the provider graph.
3. Startup readiness completes before application hooks and listener binding.
4. Existing pending embedded migrations apply when enabled.
5. Starting again with no pending versions succeeds without applying work.
6. Readiness failure closes the pool and prevents application hooks and bind.
7. Migration failure closes the pool and prevents application hooks and bind.
8. Application shutdown hooks run before the database closes.
9. With migration disabled, schema query failures remain inspectable
   `DatabaseError::Query` values.

### Facade and consumer tests

Facade tests prove all application-facing report, status, graph, diagnostic,
database, and migration APIs are available from their documented paths.
Renamed-facade consumers continue to compile. Core-only consumers continue to
compile without Axum, Diesel, pools, migrations, or `mads-common` normal
dependencies.

## Acceptance criteria

Version 0.5 is complete only when all of the following hold:

1. Existing service, repository, provider, graph, route, database, and CLI
   contracts remain compatible.
2. Core collects and evaluates official auto-configurations deterministically.
3. Public analysis remains side-effect-free and exposes ordered reports.
4. Successful applications retain the exact decision reports used to build.
5. Graph inspection distinguishes auto-configured providers explicitly.
6. Any complete-catalog provider requiring `Database` activates the linked
   Diesel default when no override exists.
7. Valid explicit configuration is still required; configuration loading is
   not implicit.
8. Missing or invalid default database configuration produces actionable
   `MADS101` without redundant `MADS003`.
9. Every application-controlled database source causes complete back-off before
   default configuration is parsed.
10. Conflicting user providers retain `MADS002`; conflicting official defaults
    produce `MADS007`.
11. Default database provisioning requires no `DatabaseConfig`,
    `DatabaseBootstrap`, or `builder.database(...)` code in application
    bootstrap.
12. Startup migration uses at most one explicitly registered embedded source,
    applies existing pending versions, and does nothing when none are pending.
13. MADS does not generate migration files or proactively validate schema when
    migration is disabled.
14. Infrastructure lifecycle starts before application hooks and stops after
    them.
15. Invalid graphs prevent pool creation and provider construction; invalid
    routes prevent connection and migration; database startup failure prevents
    application hooks and listener binding.
16. Reports and diagnostics never expose database URLs or other resolved
    configuration values.
17. The database CLI remains behaviorally unchanged.
18. Core-only dependency boundaries remain clean.
19. The workspace reports version 0.5.0 only as part of implementation and
    passes every required local, MSRV, PostgreSQL, documentation, architecture,
    and coverage gate.
20. HTTP auto-binding, module scoping, third-party registration, migration
    generation, proactive schema checks, and `mads doctor` have not leaked into
    the milestone.

## Resolved decisions

- Existing DI remains unchanged; v0.5 adds a conditional-default layer.
- The core engine is generic, while v0.5 registration is restricted to
  official integrations.
- Configuration loading remains explicit.
- Requirements use the complete provider catalog until v0.6 module scoping.
- Official capability availability is compile-time descriptor linkage.
- User overrides win before requirements and configuration are inspected.
- Ambiguous user providers remain ordinary graph errors.
- No requirement means unused configuration is not parsed.
- Evaluation is one-pass and has no chained defaults.
- Conflicting official defaults fail instead of using priority.
- Descriptor order is lexical by stable identifier.
- Analysis is side-effect-free and build applies only after valid analysis.
- Reports expose stable codes and redacted structured evidence.
- Auto-configured values have explicit graph origin and state.
- Database auto-configuration owns its complete lifecycle only when it owns the
  provider.
- Framework infrastructure surrounds application lifecycle hooks.
- Startup migrations remain embedded and require one explicit source only when
  enabled.
- Existing pending migrations are applied; no-op is success when none remain.
- MADS does not generate migration SQL or proactively check disabled
  migrations.
- HTTP auto-binding is v0.5.5, modules are v0.6, configuration UX is v0.7, and
  `mads doctor` is v0.8.
- Existing MSRV, backend, dependency pins, CLI behavior, and release gates
  remain unchanged.

There are no unresolved design decisions in this specification.
